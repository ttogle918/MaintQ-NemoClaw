# RAG 사이징 자료 — 키워드 baseline 유지 vs 벡터 전환 판단 근거 (D51 입력)

산출: **MQ-305** (Sprint 3 / Stage 1) · 데이터: `data/extracted/manual_chunks.jsonl`
재현: `uv run python data/chunk_manual.py` (아래 §2 표는 이 명령의 stdout 그대로)
대상 파일 sha256: `b67803a77238396d8d75320dc4fcd04f25ad5d4a031439a20d16320ec7342c30` (1,196,805 B)

> **이 문서의 성격.** "어떤 임베딩을 쓸까"를 고르는 문서가 **아니다**. D47 이 하이브리드 인터페이스를
> 이미 고정했고 dense scorer 는 비활성 상태다. 여기서 판단할 것은 하나 —
> **"D47 키워드 baseline 에서 벡터로 갈아탈 근거와 비용이 얼마인가."**
> **임베딩 모델·차원·벡터스토어·가중치는 이 문서가 정하지 않는다. D51 로 사람이 정한다.**

## 3. 토큰량 추정 — **실측이 아니라 근사치**

레포에 토크나이저 의존성(`tiktoken` 등)이 없어 **실제 토큰 수를 세지 않았다.** 아래는 근사식이다.

```
tokens ≈ chars / R      R = 문자/토큰 비 (한글 위주 혼합 문서에서 대략 1.2 ~ 2.0)
```

| 대상 | 문자 | R=1.2 (보수) | R=1.5 (중앙) | R=2.0 (낙관) |
|---|---|---|---|---|
| 전체 코퍼스 | 567,541 | ~473k | **~378k** | ~284k |
| iG5A 부분 | 219,261 | ~183k | ~146k | ~110k |
| S100 부분 | 348,280 | ~290k | ~232k | ~174k |
| 청크 1개(평균 548자) | 548 | ~457 | ~365 | ~274 |
| top_k=3 응답(400자 절단 후) | ≤1,200 | ~1,000 | ~800 | ~600 |

> R 값은 문헌 통념에 기댄 **가정**이고 이 코퍼스에서 측정하지 않았다. 정확한 값이 필요해지는 시점은
> API 임베딩 과금을 견적할 때뿐이며, 그때는 토크나이저 의존성을 추가해 실측할 것.

## 4. 인덱스 크기 (모델 무관, 차원만의 함수)

`1,035청크 × dim × bytes`

| 차원 | float32 | float16 |
|---|---|---|
| 384 | 1.5 MB | 0.8 MB |
| 768 | 3.0 MB | 1.5 MB |
| 1024 | 4.0 MB | 2.0 MB |
| 1536 | 6.1 MB | 3.0 MB |

**결론 한 줄: 규모가 벡터 전환의 장애물이 되지 않는다.** 어느 차원이든 수 MB이고,
1,035×dim 내적 전수 계산은 numpy 브루트포스로 밀리초 단위다 — **FAISS·Chroma 같은 벡터스토어 도입 근거가 없다.**
즉 "벡터로 갈지"의 쟁점은 성능·용량이 아니라 **의존성·오프라인·재현성**이다(§5).

## 6. 키워드 baseline 이 실제로 어디서 깨지는가 (탐침)

> **탐침 조건**: MQ-314 구현 전이라 임시 스코어러(`토큰 빈도 합 / log(청크 토큰수+10)`, model 필터 선적용)로 확인했다.
> **MQ-314 의 실제 스코어러가 아니며**, 레포에 남기지 않았다. 순위 자체가 아니라 **실패 유형**을 보기 위한 것이다.

| # | 질의 | 상위 1건 | 기대 | 판정 |
|---|---|---|---|---|
| 1 | (S100) "냉각 팬 교체 주기 확인 방법" | p.305 `6.2.8 수명 부품 진단` | 팬 수명/교체 | ✅ |
| 2 | (iG5A) "냉각팬 교체" | p.43 `3.1.5 FAN 교체하기` | 팬 교체 절차 | ✅ |
| 3 | (S100) "GFT 지락 트립이 발생했을 때 점검 절차" | p.428 `10.1.1 일상 점검` | p.416~421 트립/조치 | ❌ **흔한 낱말(‘점검’)이 희귀 토큰(‘지락’·GFT)을 압도** |
| 4 | (iG5A) "과전류 트립이 반복될 때 원인과 대책" | p.60 `4.6 운전 상태 모니터링 방법` | p.204~206 `12.2 고장 대책` | ❌ 같은 원인 |
| 5 | (iG5A) "인버터가 갑자기 멈췄는데 무엇을 먼저 확인해야 하나요" | p.47 `3.2 주변 기기 구성` | 12.3/12.4 고장 진단 | ❌ **자연어 질의 — 공유 토큰이 거의 없음** |
| 6 | (S100) "모터가 돌지 않아요" | p.211 자동 튜닝 표 | 시운전/트립 | ❌ 같은 원인 |

**읽는 법 — 실패가 두 종류로 갈린다.**

1. **3·4번은 dense 없이도 고칠 수 있다.** 원인이 의미 이해 부족이 아니라 **가중치 부재**다.
   IDF 가중(BM25류)만 넣어도 ‘점검·인버터·발생’ 같은 문서 전반에 깔린 낱말의 지배력이 사라진다.
   현재 스프린트 명세의 키워드 스코어링은 "토큰 포함 빈도 / 청크 길이 정규화"라 **IDF 가 없다** → §7-4 결정 요청.
2. **5·6번은 키워드로 원리적으로 안 된다.** 정비사 발화("갑자기 멈췄어요", "안 돌아요")와 매뉴얼 문어체 사이에
   공유 토큰이 없다. D47 이 dense 를 넣기로 한 이유가 이 칸에 그대로 나타난다.

**따라서 판단 순서를 제안한다(결정은 사람):**
**① IDF 가중을 먼저 적용해 3·4형 실패를 제거 → ② 남는 실패가 5·6형(자연어)뿐인지 확인 → ③ 그 잔여량이 D30 인용률 목표를 위협할 때 dense 를 켠다.**
이 순서가 아니면 "벡터를 넣었더니 좋아졌다"의 상당 부분이 실은 IDF 효과인지 구분되지 않는다.

**지표 연결**: D30 인용률 분모는 `lookup.manual_page` **+ `rag.chunks[*].page`** 합집합이다.
5·6형 실패는 rag 결과 page 를 엉뚱하게 만들어 **인용률에 직접 반영된다** — 검색 품질이 그냥 UX 문제가 아니라 평가 수치다.

## 8. 이 문서가 정하지 않은 것 (경계 명시)

- 임베딩 모델·벡터스토어·하이브리드 가중치 — **D51, 사람 결정**. MQ-305 는 수치와 실패 유형만 제공한다.
- 검색 구현·스코어링 — `mcp_server/rag.py` (D48, MQ-314). `backend/rag/` 는 만들지 않았다.
- 인쇄 페이지 환산 — `backend/manifest.py` (D32·D49, MQ-312). 청크 데이터에 `print_page` 는 없다.
