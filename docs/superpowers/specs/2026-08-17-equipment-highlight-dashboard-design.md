# 설비 하이라이트 대시보드 + 재고 연동 + 생애주기 경고 — 설계

**작성일**: 2026-08-17 · **브레인스토밍 세션**: 같은 날 대화(Sprint 9 종료 직후) · **상태**: 사용자 승인 대기

## 0. 배경

Sprint 9(수리 증빙 서명)가 끝난 뒤, 사용자가 다음 스프린트 화면 작업에 대해 의논을 요청했다. 초기 요청은 4개 서브시스템이 섞여 있었다:

- **A.** 이상탐지 후 수리 판정 시 창고 재고 확인 → 없으면 비용 발생(발주)
- **B.** 재고 없을 때 FinAllQ로 자금조달 통신
- **C.** 설비 이미지/3D 화면에 부위별 원형 하이라이트(빨강=이상탐지, 파랑=최근수리, 주황=곧점검) + 옆 목록
- **D.** 생애주기 기반 "곧 수리 필요" 경고색

논의 끝에 **B는 백로그(P34에 사례로 편입) · A·D·C는 이번 설계 대상**으로 범위를 좁혔다. 설계 중 A의 "발주하러 가기" 버튼이 "화면에서 직접 초안 생성"이라는 훨씬 큰 요청(3개 쓰기 도구 전부에 영향)으로 번져 이것도 **별도 백로그(P39)로 분리**했다.

## 1. 범위

**이번 설계에 포함**: A(재고 자동 표시 + 우측 드로어) · D(생애주기 경고 mock 데이터) · C(설비 하이라이트 대시보드, 목록→드릴다운)

**명시적으로 제외** (백로그 이관, `docs/07_BACKLOG.md` 참고):
- P34: FinAllQ 자금조달 연동(B) — A2A 경계, QMesh 착수 후
- P39: 발주서·처분서·수리증빙 화면 직접 생성 + 수정 가능한 초안 — 이번엔 A의 "발주하러 가기"를 **채팅 이동 + prefill**(기존 처분서 흐름 선례, `docs/06_REPO_API.md §2.2` 상단 주석)로만 처리

**하이라이트 대상 부품은 매뉴얼 도면에 실제로 라벨된 것만** — 냉각팬·키패드·제어보드(제어보드는 근사 배치, 아래 §4-3). `parts` 카탈로그의 나머지 30여 종은 하이라이트 없이 목록에서만 텍스트로 노출(해당 시).

## 2. A — 재고 연동

### 2-1. 표시 위치
`RepairValuePanel`(`frontend/components/asset/RepairValuePanel.tsx`, Sprint 9 MQ-914 산출물)에서 `assess_repair_value` 판정이 나오면 **자동으로** `failed_part` 기준 재고를 조회해 함께 표시한다(버튼 클릭 불필요).

### 2-2. 재고 상세 — 우측 드로어
`CriticalityDrawer.tsx`(Sprint 9 기존 산출물)와 **동일한 UI 패턴**(fixed-position 오버레이 + 오른쪽 슬라이드) 재사용 — 새 컴포넌트 `InventoryDrawer.tsx`를 같은 패턴으로 만든다. 재고 요약을 클릭하면 열리고, 안에는:
- 재고 수량(있음/없음, 부족 시 안전재고 대비 수치)
- 공급사 비교(기존 `search_inventory`·`get_supplier_quotes` 응답 재사용)
- **"발주하러 가기" 버튼** — 클릭 시 `/technician` 채팅 화면으로 이동하며 입력창에 `"{equipment_id}의 {part_no} 재고 부족, 발주해줘"` 형태로 prefill. **실제 `create_po_draft` 호출은 여전히 에이전트가 채팅에서 한다** — 새 쓰기 경로를 열지 않는다(P39 완성 전까지의 임시 처리, 명시적으로 사용자와 합의된 사항).

### 2-3. 데이터
새 데이터 불필요 — 기존 `search_inventory`(코어 도구) 그대로 재사용.

## 3. D — 생애주기 경고

### 3-1. 판정 기준
**새 mock 필드**로 간다(기존 `residual_curve`·`repeat_failure` 재사용 안 함 — 그 둘은 "자산 재무적 잔가"와 "실제 진단 기반 반복고장"이라는 다른 개념이라 "다음 점검일"과 직접 대응하지 않는다는 게 이번 논의의 결론).

### 3-2. 데이터 모델
신규 소형 시드 테이블(가칭 `part_lifecycle_mock`):

```sql
CREATE TABLE part_lifecycle_mock (
  equipment_id TEXT NOT NULL REFERENCES equipment,
  part_no      TEXT NOT NULL REFERENCES parts,
  next_maintenance_due DATE NOT NULL,
  PRIMARY KEY (equipment_id, part_no)
);
```

**범위**: §4-3의 하이라이트 대상 부품(냉각팬·키패드·제어보드에 대응하는 `part_no`) × 9자산 중, 그 부품이 실제로 해당 모델에 쓰이는 조합만 시드. 최대 27행, 실제로는 그보다 적음. 날짜는 데모 다양성을 위해 임박·여유·과거(이미 지남) 섞어서 부여.

**⚠ 구현 계획 단계에서 확정할 것**: 이 테이블을 `data/seed.py`에 새 절로 추가할지, 별도 JSON 시드 파일로 둘지는 기존 컨벤션(예: `related_parts.seed.json` 선례)을 참고해 `writing-plans` 단계에서 정한다.

## 4. C — 설비 하이라이트 대시보드

### 4-1. 화면 구조 (신규 라우트 2단계)

**① 목록** (가칭 `/technician/equipment-status`)
- 9개 자산을 카드/행으로 나열
- 각 카드에 상태 배지(예: 🔴1 🟠1 — 그 자산에 걸린 하이라이트 개수)
- 카드 클릭 → ②로 드릴다운

**② 하이라이트 상세** (모델 단위 도면 — 같은 모델의 설비는 도면을 공유, 상태만 자산별로 다름)
- **기본(default) 뷰**: 매뉴얼 도면 전체 이미지 위에 3개 하이라이트 부위(냉각팬·키패드·제어보드) 원형 오버레이. 상태 없는 부위는 원래 라인아트 그대로(투명, 색 없음)
- **옆 목록**: 하이라이트된 부위만 텍스트로도 나열 — 색 점 + 부품명 + 한 줄 요약. **도면 위 원과 옆 목록 항목은 같은 상세 패널을 연다**(둘 다 진입점, 하나의 상태)
- **클릭 시 확대 상세**: §4-4 참고

### 4-2. 이미지 소스 — 매뉴얼 도면 그대로 사용 (라이선스 고지)

`data/raw/manifest.json`에 이미 등록된 두 매뉴얼에서 확보:

| 모델 | 파일 | 물리 페이지 | 그림 | 용도 |
|---|---|---|---|---|
| iG5A | `iG5A_User_Manual_Standard_KR_210303.pdf` | 22 | 그림 1-1(완제품 상태)·1-2(전면 덮개 제거 시) | 기본 뷰 |
| iG5A | 〃 | 23 | 그림 1-4(냉각 팬 교체 시) | 냉각팬 클릭 확대 뷰(실제 근접 이미지 존재) |
| S100 | `S100_Manual_Korean_V4.2.pdf` | 19 | 1.2.1절 분해도 | 기본 뷰 |

`manifest.json`의 라이선스 조항: *"저작권 LS ELECTRIC. 비상업적 학습·포트폴리오 목적. 원본 재배포 금지(git 제외)."* 지금까지는 텍스트만 추출해 왔는데, 이번엔 **이미지 자체를 프론트엔드 정적 자산으로 git에 커밋**한다 — 사용 성격이 달라지므로:
- 화면에 **출처 고지**(예: "LS ELECTRIC iG5A 사용설명서 p.22")를 항상 표시한다.
- 이 프로젝트가 이미 "비상업적 학습/포트폴리오"로 스스로 규정한 사용 목적 안에 있다는 전제 — **사용자가 최종 책임 판단**(에이전트가 임의 결정하지 않음, 이미 이번 대화에서 "매뉴얼 도면 그대로 사용"으로 명시 승인받음).
- 원본 PDF는 계속 `data/raw/`(git 제외, 절대규칙 5)에만 둔다. 크롭된 PNG만 `frontend/public/` 등에 커밋.

### 4-3. 하이라이트 좌표 — 정적 설정 (DB 아님)

모델별 하드코딩 좌표(픽셀 또는 %) — 코드 상수로 관리, 실물 도면과 1:1 매칭이라 DB화할 이유가 없다.

```ts
// 예시 형태 (정확한 좌표는 구현 시 이미지 보고 확정)
type Hotspot = {
  part_no: string;       // parts.part_no 와 매칭 — 있으면 실 데이터 조회 가능
  label: string;
  x: number; y: number; r: number;  // 기본 도면 위 좌표
  detail_image?: string;  // 확대 시 쓸 별도 근접 이미지 경로(있으면)
  approximate?: boolean;  // true 면 "정확한 위치 아님" 고지 필요
};

const IG5A_HOTSPOTS: Hotspot[] = [
  { part_no: "FAN-IG5-01", label: "냉각팬", x: .., y: .., r: .., detail_image: "ig5a_fan_detail.png" },
  { part_no: "KPD-IG5-01", label: "키패드/로더", x: .., y: .., r: .. },
  { part_no: "PCB-IG5-CTRL", label: "제어보드", x: .., y: .., r: .., approximate: true },
];
// S100_HOTSPOTS 동일 구조
```

**제어보드(`PCB-IG5-CTRL`/`PCB-S100-CTRL`)는 도면에 정확한 라벨이 없다** — iG5A 그림 1-2는 스위치·단자대만 라벨하고, S100 분해도는 "인버터 본체" 전체를 한 덩어리로만 라벨한다. `approximate: true`로 표시하고, 화면에도 "정확한 부품 위치가 아니라 대략적인 영역입니다" 같은 고지를 단다(D65 태도와 같은 정직성 원칙 — 이 프로젝트 전반에 이미 깔린 관행).

### 4-4. 클릭 시 확대 상세

| 부위 | 확대 방식 |
|---|---|
| 냉각팬 | 매뉴얼의 실제 근접 이미지(그림 1-4, "인버터 냉각 팬을 교체할 때") 그대로 전환 |
| 키패드 · 제어보드 | 기본 도면을 그 부위 좌표 중심으로 CSS 크롭/확대(별도 이미지 없음) |

확대 패널에 표시할 텍스트는 **기존 진단 데이터 재사용**(신규 데이터 생성 안 함, 이번 대화에서 명시 확인):
- 🔴 상태면 관련 `error_codes.causes`·`actions` 원문
- 🔵 상태면 관련 `repair_records`의 서명 정보(수리 일자·작업자 등)
- 🟠 상태면 `part_lifecycle_mock.next_maintenance_due`

### 4-5. 색상 판정 규칙 (부품 단위, 우선순위 순)

| 우선순위 | 색 | 조건 | 데이터 출처 |
|---|---|---|---|
| 1 | 🔴 이상탐지 | 이 부품과 연결된 에러코드가 진단됐고, 그 이후 서명된 수리 기록이 없음(="아직 안 고침") | `error_history` + `related_parts`(에러코드↔부품 매핑) + `repair_records.signed_at` 비교 |
| 2 | 🔵 최근 수리 | 최근 N일 내 서명된 수리 기록이 있고, 그 이후 새 에러 진단이 없음 | `repair_records.signed_at`(N=90일 제안, 구현 계획에서 확정) |
| 3 | 🟠 곧 점검 | `part_lifecycle_mock.next_maintenance_due`가 임박(M일 이내, M=60일 제안) — 단 위 1·2에 해당하지 않을 때만 | `part_lifecycle_mock`(§3) |
| — | (색 없음) | 위 셋 다 해당 없음 | — |

"이상탐지"는 **새 탐지 로직(센서·임계치)을 만들지 않는다** — 기존 에러코드 진단·수리 기록 데이터를 재해석하는 것뿐이다(이번 대화에서 명시 확인, 이 프로젝트에 실시간 텔레메트리 데이터 자체가 없다).

### 4-6. 백엔드 변경

- 색상 판정 로직이 여러 테이블 조인(에러이력 + 수리기록 + mock 생애주기)이라 프론트에서 여러 API를 조합하는 것보다 **얇은 집계 엔드포인트 1개**(가칭 `GET /api/assets/{id}/hotspot-status`)를 백엔드에 두는 편이 나아 보인다. 다만 정확한 필요 여부·엔드포인트 형태는 **구현 계획(writing-plans) 단계에서 확정**한다 — 기존 `data/maint_value.py` 패턴(계산 로직은 `data/`, MCP·REST 둘 다 위임)을 따를 가능성이 높다.
- 신규 mock 테이블(`part_lifecycle_mock`)은 읽기 전용 — 쓰기 도구 신설 없음(D10과 무관).
