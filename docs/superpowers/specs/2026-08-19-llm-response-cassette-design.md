# LLM 응답 카세트 — 개발 가속용 응답 캐시 — 설계

**작성일**: 2026-08-19 · **브레인스토밍**: 같은 날 대화(Sprint 13 Stage 1 직후) · **상태**: 사용자 승인 완료

## 0. 배경 — 왜 필요한가

사용자가 겪는 통증: **`/scenario-smoke` · `/run-eval` · curl 로 API 직접 호출** 할 때마다 오래 걸린다. 그런데 **검증하려는 대상은 LLM 출력이 아니라 백엔드 실행**이다 — 라우터·SSE·MCP 왕복·DB 쓰기가 제대로 도는지.

### 0-1. 기존 수단으로는 안 된다 (실측 확인)

- **`ScriptedClient`**(`backend/agent/llm.py:42`)는 턴별 델타를 **손으로 적어 넣는** 구조이고, 스크립트보다 호출이 많으면 `AssertionError` 를 던진다. 결정적 단위 테스트용이지 *"실제 백엔드를 돌리되 LLM 만 건너뛰기"* 용이 아니다.
- **`get_client()` 는 키가 없으면 실패한다**(D40, `llm.py:305`) — *"가짜 응답을 진짜로 착각하는 사고를 막기 위해"* 폴백하지 않는다. `backend/routers/chat.py:190` 이 이 태도를 다시 적어 뒀다.
- 결과: **개발 중 실 LLM 호출을 피할 경로가 없다.** 회귀 스파이크 872건은 `ScriptedClient` 로 돌아 영향이 없지만, 스모크·평가·수동 API 호출은 전부 실 호출을 탄다.

### 0-2. 현재 설정 (실측)

`MAINTQ_LLM_PROVIDER=gemini` · `MAINTQ_LLM_MODEL=gemini-2.5-flash` · 프로바이더는 **`("gemini","anthropic")` 2종뿐**(`llm.py:297`). 프로세스 환경에 `GEMINI_API_KEY`·`GOOGLE_API_KEY` 존재. `OPENAI_API_KEY` 도 있으나 **MaintQ 가 쓸 수 없다**(프로바이더 목록 밖).

## 1. 목표 / 비목표

**목표**: 반복 실행 시 **LLM 응답만** 재생해 백엔드 검증을 빠르게 한다. 도구 실행·DB 쓰기·SSE 발행은 **진짜로 돌아야 한다**.

**비목표 (명시적 범위 밖)**:
- **시연 프리워밍 캐시** — 배포용 커밋 캐시. 같은 파일 형식이라 나중에 얹을 수 있고 지금 설계가 그것을 막지 않는다
- **Redis** — 아래 §4-3
- **`build.nvidia` 프로바이더 확장** — 별도 스펙. 이 스펙과 독립이다
- **모델 교체(`gemini-2.5-flash-lite`)** — `.env` 한 줄이라 지금도 가능하며 이 스펙과 무관. ⚠ 다만 **캐시를 먼저 넣고 나서 모델 실익을 재는** 순서를 권한다 — 반복 실행이 0초·0원이 되면 모델 교체의 실익 자체가 줄어든다
- **배포**(Cloud Run·Vercel) — SQLite 휘발성·MCP 자식 프로세스 등 캐시와 무관한 문제가 더 크다. 백로그 **P14**(docker-compose) 와 맞물리는 별도 프로젝트

## 2. 구조 — 데코레이터 하나

`LlmClient` 프로토콜(`llm.py:36`)을 구현하는 **데코레이터** `CachingClient(inner)`. 기존 `GeminiClient`·`AnthropicClient` 를 감싼다.

**변경면은 3곳뿐이다**: ⓐ `llm_cache.py` 신규 ⓑ `get_client()` 가 마지막에 감싸기 ⓒ `run_turn` 에서 **히트 시 `trace.replay` 를 켜는 한 지점**(§5-2). 라우터·MCP·프론트·평가 채점 코드는 **무변경**이다.

⚠ ⓒ 를 빼면 캐시 히트가 지표에 섞여도 아무도 모른다 — 이 스펙에서 **가장 빠뜨리기 쉬운 한 줄**이라 회귀 4번이 이것만 본다.

```
run_turn → CachingClient.stream() ─┬─ 히트 → 기록된 델타 재생 (네트워크 0)
                                   └─ 미스 → inner.stream() 실행하며 델타 기록
```

**도구는 그대로 실행된다.** 캐시가 대신하는 것은 LLM 응답뿐이라 MCP 왕복·DB 쓰기·SSE 발행·trace 저장은 실제로 일어난다. 이것이 이 설계의 목적 그 자체다.

**배치**: `backend/agent/llm_cache.py` (신규). `get_client()` 가 마지막에 감싼다.

## 3. 켜고 끄기 — 기본은 꺼짐

`MAINTQ_LLM_CACHE` 가 **`on`** 일 때만 동작한다(그 밖의 값·빈 값·미설정은 전부 꺼짐). 기본 `off` 이므로 **설정하지 않으면 현재 동작이 그대로다.**

D40 의 태도(*"테스트용 스크립트 응답으로 자동 대체하지 않는다 — 가짜 응답을 진짜로 착각하는 사고를 막기 위해"*)를 따라 **명시적 옵트인**으로 둔다. 빈 값은 미설정과 같게 처리한다(D56 선례 — `.env` 의 `KEY=` 는 미설정).

## 4. 키 · 값 · 저장

### 4-1. 키

```
sha256(canonical_json({provider, model, system, messages, tools}))
```

`model`·`provider` 를 키에 넣는 이유: 모델을 바꾸면 **반드시 미스가 나야 한다.** 안 그러면 flash 로 만든 응답을 flash-lite 결과로 착각한다.

### 4-2. 값

`LlmDelta = tuple[str, object]`(`llm.py:32`) 시퀀스를 직렬화한다. 종류는 3종뿐이라 단순하다:

| kind | payload | 직렬화 |
|---|---|---|
| `text` | `str` | 그대로 |
| `tool_use` | `ToolUse(id, name, input)` 데이터클래스 | `asdict` |
| `end` | stop reason | 그대로 |

### 4-3. 저장 — 파일, git 미추적

`data/cache/llm/<key>.json`, **`.gitignore`**. 개발 보조물이라 언제 지워도 된다.

**Redis 를 쓰지 않는 이유**: 이 프로젝트는 의도적으로 docker 를 안 쓴다(D27 — uv+venv 로 충분, docker-compose 는 백로그 P14). Redis 는 *"테스트를 빠르게 하려고 서버를 하나 더 띄워야 하는"* 상태를 만든다. Redis 가 값을 하는 지점(TTL·동시성·인스턴스 간 공유)은 **단일 개발자·단일 프로세스 데모**(`SessionStore` 독스트링이 *"프로세스 메모리 세션 저장소. 단일 사용자 데모 전제"* 라고 못박음)에서 쓸 일이 없다.

**`data/external/store.py`(D103)를 재사용하지 않는 이유**: 그것은 **git 추적·append-only 외부 원본**용이고, 이 캐시는 **미추적·언제든 삭제 가능한 개발 보조물**이다. 성격이 정반대라 한 모듈에 담으면 규약이 흐려진다.

## 5. 급소 — 캐시 히트는 D55 재생으로 표식한다

**이 설계에서 가장 중요한 결정이다.**

캐시 히트가 섞인 세션은 `replay: true` 표식을 달고, **D55 의 기존 기계장치가 자동으로 지표 분모에서 제외**한다.

### 5-1. 왜 새 표식을 만들지 않나

1. **의미상 맞다** — 캐시 히트는 기록된 응답의 재생이다.
2. **깜빡해도 안전하다** — 캐시 끄는 걸 잊고 평가를 돌리면 지표가 **조용히 오염되는 대신 "제외됨"으로 드러난다.** 이것이 "지우고 돌린다"보다 나은 이유다. 지우는 것은 깜빡하면 아무도 모른다.
3. **회귀가 이미 있다** — `spikes/eval_replay_guard.py` **16건**이 이 동치성을 지킨다. 특히 E 항목(*"표식 위치 무관성 — 부분 오염도 전체 배제"*)이 그대로 적용된다. **새 회귀를 만들 필요가 없다.**

### 5-2. 배선 (실측으로 확인함)

- `TraceWriter.replay` 는 생성자 인자이자 **평범한 속성**(`backend/agent/trace.py:87`)이고 `:162~163` 이 이벤트 payload 에 주입한다 → **턴 도중에 켤 수 있다.**
- `run_turn` 은 `stream()` 을 **어떤 trace 이벤트보다 먼저** 호출한다(`loop.py:395`, tool_call 발행은 그 뒤) → 첫 히트에서 켜면 그 턴의 모든 traced 이벤트에 표식이 붙는다.
- `eval/score.py:153 has_replay()` 는 `any()` 라 **부분 오염도 세션 전체가 걸린다**.
- `CachingClient` 는 조회를 `stream()` 진입 시 동기적으로 끝내고 `last_hit` 을 노출한다. `run_turn` 이 그 값을 읽어 `trace.replay = True` 로 켠다.

⚠ `token` 이벤트는 표식 대상이 아니다 — traces 에 저장되지 않아(D41) 판정 소스가 아니다. D55 본문이 이미 그렇게 정해 뒀다.

### 5-3. 결과 — `/run-eval` 두 모드

| 모드 | 캐시 | 지표 | 쓰임 |
|---|---|---|---|
| **기본** | off | **인정** | 지표를 잴 때 |
| **`--replay`** | on | **미인정**(D55 제외) | 채점·집계·배선을 고칠 때 빠르게 |

⛔ **`--replay` 로 낸 수치를 실적으로 인용하지 않는다.** 집계가 이미 분모에서 빼므로 애초에 수치가 나오지 않는다.

## 6. 정직성 — 히트율을 인쇄한다

### 6-1. 알려진 한계

`run_turn` 은 `messages = store.history(session_id)`(`loop.py:344·525`)로 **전체 이력**을 넘기고, 한 턴에 LLM 을 여러 번 부른다. 이력에는 도구 결과가 섞이는데 그중 `create_po_draft` 의 `po_id`(max+1) · 타임스탬프처럼 **실행마다 달라지는 값**이 있다. 따라서 **다중 호출 턴에서는 2번째 호출부터 키가 어긋나 미스가 날 수 있다.**

### 6-2. 미리 정규화하지 않는다

휘발성 필드를 지우고 해싱하면 **다른 입력에 같은 응답을 주는 더 나쁜 버그**가 된다. 대신:

- 실행 종료 시 **`캐시 히트 N/M (히트율 X%)`** 을 인쇄한다
- 히트율이 낮으면 **그때 원인을 실측해** 좁힌다. 지금 추측으로 풀지 않는다

이 태도는 `data/extract_triage.py` 가 *"기대값은 assert 로 죽이지 않는다 — 계측기가 입력을 검열하면 계측기가 아니다"* 라고 쓴 것과 같다.

## 7. 회귀

신규 pytest(`backend/agent/test_llm_cache.py`) 또는 스파이크 1종. **네트워크를 절대 타지 않는다** — `inner` 를 폭파 스텁으로 둔다.

| # | 검사 |
|---|---|
| 1 | `MAINTQ_LLM_CACHE` 미설정·빈 값 → **캐시 비활성**, `inner` 그대로 통과 |
| 2 | 미스 → `inner.stream()` 호출 + 델타 기록 |
| 3 | 히트 → **`inner` 미접촉**(폭파 스텁이 증명) + 델타 동일 재생 |
| 4 | 히트 시 `last_hit=True` → `TraceWriter.replay` 가 켜지고 이벤트에 `replay: true` |
| 5 | 키가 `model`·`provider` 포함 → 모델만 바꾸면 **미스** |
| 6 | 델타 3종(`text`·`tool_use`·`end`) 직렬화 왕복 동일 (`ToolUse` 필드 보존) |
| 7 | 캐시 디렉터리가 `.gitignore` 에 있다 (**양성 축**: `git check-ignore` rc + 스캔 대상 > 0) |

**기존 `eval_replay_guard` 16건은 무변경으로 그대로 값을 한다** — §5-1 의 3번 근거.

## 8. 새 D-결정 1건

⚠ **번호 주의**: `10_DECISIONS.md` 는 현재 **D103** 까지이고 **D104 는 Sprint 13 Stage 2(MQ-1307)가 선점**했다(Elice 도입). 이 스펙은 **D105** 를 쓴다 — 두 작업이 병렬로 진행되면 번호가 충돌하므로 착수 시 실제 마지막 번호를 다시 확인할 것.

**D105 — LLM 응답 캐시는 기본 꺼짐이고, 히트는 D55 재생으로 표식해 지표 분모에서 제외한다.**

대안: ⓐ 캐시 없음(현행) ⓑ 평가 실행 전 캐시 삭제 ⓒ 캐시 전용 새 표식 신설.
근거: ⓑ 는 **깜빡하면 조용히 오염**되고 다른 용도의 캐시까지 지운다 — 실패가 침묵하는 설계다. ⓒ 는 `eval_replay_guard` 16건과 `has_replay()` 를 중복시키고, *"재생과 캐시가 무엇이 다른가"* 를 앞으로 계속 설명해야 한다. D55 가 이미 *"부분 오염도 전체 배제"* 를 정해 뒀으므로 재사용이 자연스럽다. ⓐ 는 실 통증을 방치한다.
⚠ **함께 명시**: 캐시 히트는 **가짜 응답이 아니라 기록된 실제 응답**이다. 그래도 표식하는 이유는 *"언제 만들어진 응답인지"* 가 지표의 전제이기 때문이다(모델·프롬프트가 그 사이 바뀌었을 수 있다).

## 9. 스테이지 경계 (실행 계획 시)

- **Stage 1** — `llm_cache.py` + `get_client()` 배선 + `.gitignore` + D105 등재 (네트워크 0)
- **Stage 2** — `run_turn` 의 replay 플래그 배선 + `/run-eval --replay` 모드
- **Stage 3** — 회귀 7건 + 히트율 인쇄 + 실측(스모크 1회 전후 시간 비교)

⚠ **Stage 3 의 실측이 이 스펙의 성공 판정이다.** "빨라졌다"를 체감이 아니라 **초 단위 실측**으로 적는다. 히트율이 낮아 실익이 없으면 그 사실을 그대로 기록한다 — §6-2 의 태도.
