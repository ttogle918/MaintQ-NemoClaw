## 0. 배경

`docs/07_BACKLOG.md` 점검 중 P31·P28 을 다음 작업으로 고르면서, 두 항목의 전제가 **실측과 어긋나 있다**는 것이 드러났다.

### 0-1. 저장소 안에 같은 결측에 대한 진단이 셋 있고, 아무도 대조하지 않았다

정본 `data/extracted/error_codes.json` 65건 중 `actions` 결측은 **34건**(S100 25 / iG5A 9)이다. 이 34건의 성격에 대해 저장소가 세 가지 다른 답을 갖고 있다:

| # | 출처 | 진단 | 함의 |
|---|---|---|---|
| 1 | `error_codes_actions.candidate.json` 의 `_pending_review` (MQ-911, Sprint 9) | 35건 중 **28건 = 매뉴얼에 조치문이 원래 없음** (S100 9.2 조치사항표 p.420~421 에 항목 자체가 없음) | 어떤 기술로도 회수 불가 |
| 2 | `data/analysis/extract_triage.md` (MQ-902, Sprint 9) | S100 25건은 **`CELL_SPLIT`** (p.416~419) — 파서 수정 대상. 재-OCR 후보는 **1페이지 45원**뿐 | 파서를 고치면 회수 |
| 3 | `docs/07_BACKLOG.md` P31 ⓑ | S100 26건 = 셀 내 줄바꿈 분해 실패 → **재추출 후보** | 재추출로 회수 |

2·3 은 서로 맞고 **1 과 정면으로 충돌한다.** 셋 다 Sprint 9 산출물인데 서로를 참조하지 않는다.

추가로, triage 는 스스로 `ANCHOR_CONFLICT` 경고를 띄운다 — `ig5a-manual p.202` 의 `SOURCE_MISSING` 라벨에 대해 *"근거가 없는 라벨이므로 '소스를 바꿔야 풀린다'로 읽지 마세요"* 라고 출력한다. 즉 **1번 진단의 일부는 도구 자신이 신뢰하지 말라고 표시해 둔 상태**다.

### 0-2. 백로그 기술이 낡아 있었다 (이번 점검에서 확인한 것)

- **P31** — *"선행은 triage — 지금은 추출 품질을 재는 단계가 없다"* → **틀렸다.** `data/extract_triage.py` 가 Sprint 9(MQ-902)부터 있고, 부재 주장에 양성 축 2개(`code_tokens_found`·`codes_with_actions`)를 걸어 두었으며 `estimate_ocr_cost(won_per_page=45)` 까지 있다.
- **P31** — *"ⓐⓑ 회수 완료"* → **틀렸다.** 실제 회수는 3건뿐이고 35건이 `_pending_review` 에 남아 있다. (2026-08-19 커밋 `28c4f69` 에서 백로그 정정 완료)
- **P22** — 잔여에 `KR-CITA-ENF-31` 사람 승인이 남아 있다고 적혀 있었으나 2026-08-13 완료. (같은 커밋에서 정정 완료)
- **P28 ⓐ** — 여전히 참이다. `fetch_laws.py:429` 의 `payload`(법제처 원본 응답)는 파싱 후 **버려진다**.

### 0-3. 전제 변화 — 비용은 병목이 아니다

InsuQ 의 P31 원본 목적은 *"유료 OCR 로 다시 읽어야 할 페이지를 고른다"* 는 **비용 선별**이었다. MaintQ 에서는 그 목적이 거의 의미가 없다 — triage 산정 재-OCR 대상이 1페이지(45원)이고, 사용자 Elice 예산이 **40,000원**이다. 병목은 돈이 아니라 **어느 진단이 맞는지 아무도 모른다는 것**이다.

## 1. 목표 / 비목표

**목표**: 34건 결측에 대한 세 진단의 불일치를 **독립 판독기로 해소**하고, 결과를 회귀로 고정한다.

**명시적 비목표**:
- **"회수"는 목표가 아니라 결과다.** 부재가 사실로 확정되는 것도 똑같이 유효한 산출이다. 회수 건수를 성공 지표로 삼지 않는다 — 그렇게 하면 없는 조치문을 만들어내는 압력이 생기고, 이는 절대규칙 3(안전 문구는 매뉴얼 근거 없이 생성 금지) 위반으로 직결된다.
- **파서 수정은 이번 범위가 아니다.** 판독 결과가 `CELL_SPLIT` 을 지지하면 그 사실을 기록하고 끝낸다. 파서 개선은 별도 작업.
- **InsuQ `quality_triage.py` 이식은 하지 않는다.** 그 모듈은 chunk report 를 입력으로 하는 unknown-unknowns 탐지기인데, MaintQ 는 결측 코드와 대상 페이지를 **이미 알고 있다**(known-knowns). 대응물인 `data/extract_triage.py` 가 이미 있다.
- 부품 특정 정확률(40.0%) 개선 — 이건 P32(부품 품번) 축이고 `actions` 와 무관하다.

## 2. 구조 — 2단

InsuQ 는 3단(triage → elice → replace)이었으나 MaintQ 는 ①이 이미 있어 **2단**이다.

```
① triage        [기존] data/extract_triage.py — 신규 코드 0. 재실행만 한다.
② Elice 재판독  [신규] 34페이지를 독립 판독기로 다시 읽고 raw JSON 을 캐시한다.
③ 3자 대조      [신규] 파서 주장 vs triage 라벨 vs Elice 판독 → 검수 패키지.
```

### 2-1. ① triage (기존 재사용)

`uv run python data/extract_triage.py` 를 그대로 돌린다. 산출물 `data/analysis/extract_triage.md` · `data/extracted/extract_triage.json` 이 ②의 대상 페이지와 ③의 대조 입력이 된다.

⚠ 이 모듈은 정본을 쓰지 않고 DB 를 열지 않는다(D99 격리). 그 경계를 유지한다.

### 2-2. ② Elice 재판독 (신규)

`../InsuQ/ai-engine/insuq_ai/ingest/elice_docvision.py` 를 MaintQ 로 이식한다. 이식 대상은 **모델이 아니라 구조**다:

| 이식하는 것 | 이유 |
|---|---|
| `normalize_base_url()` | URL·모델 ID·콘솔 UUID 혼동으로 InsuQ 가 실제로 3회 실패한 이력이 주석에 있다 |
| 페이지 단위 분할 업로드(`_single_page_pdf`) | **페이지 단위 과금**이라 통째로 올리면 안 된다 |
| raw JSON 캐시 + `cache_path()` | 같은 페이지를 두 번 사지 않는다. **이것이 P28 ⓐ 의 첫 구현체다**(§3) |
| `allow_purchase=False` 기본 | 캐시 미스 시 네트워크를 타지 않고 즉시 예외. 실수로 돈이 나가지 않는다 |
| `PRICE_PER_PAGE_WON = 45` 상수 | 비용 산정이 리포트와 어긋나지 않는다 |
| `DEFAULT_CONFIGS = {"do_chart_conversion": True}` | **표를 HTML 로 받는다** — 뭉개진 표 복원이 이 폴백의 주 목적이고 MaintQ 의 실패 모드와 정확히 같다 |
| 제출→폴링 종료 상태 `{"failure","failed","cancelled"}` | 규격 오타로 무한 폴링에 빠지지 않게 고정한 것 |

**이식하지 않는 것**: InsuQ 의 chunk 교체 로직(`elice_replace.py`) — MaintQ 는 chunk 파이프라인이 아니라 표 파서라 대응물이 없다.

**배치**: `data/external/elice_docvision.py` (신규 디렉터리). `data/rules/` 가 룰 계층을 갖는 것과 같은 형태.

### 2-3. 판독 범위 — 34페이지

| 대상 | 페이지 | 근거 |
|---|---|---|
| S100 §9.1 트립/경보표 + §9.2 조치사항표 + 앞뒤 여유 | p.412~425 (14p) | 결측 25건이 전부 여기. 표가 구간 밖으로 이어지는지 봐야 부재 주장을 판정할 수 있다 |
| iG5A 트러블슈팅 조치 구간 + 앞뒤 여유 | p.20~31 (12p) | 결측 9건의 조치문 후보 위치 |
| iG5A 표준본 보호기능표 + 앞뒤 여유 | p.200~207 (8p) | `p.202` `SOURCE_MISSING` 라벨이 `ANCHOR_CONFLICT` 로 오염된 지점 |

**합계 34페이지 · 1,530원 · 예산 40,000원의 3.8%.** (구간 길이 14+12+8 의 산술이며, 실행 전 고지 출력이 이 값을 다시 찍는다)

⚠ **이는 triage 권고(1페이지 45원)를 의도적으로 넓힌 것이다.** triage 는 *"`CELL_SPLIT` 은 파서 수정 대상이라 재-OCR 로 풀리지 않는다"* 고 보는데, **그 전제는 Elice 의 표 HTML 변환을 고려하지 않았다.** InsuQ 가 Elice 를 도입한 이유가 정확히 "뭉개진 표 복원"이다. 이 판단이 틀리면 45원이 1,530원이 되고, 맞으면 25건이 회수 후보가 된다. 예산 대비 3.8% 라 걸어볼 값이라고 판단했다 — **판단의 주체와 근거를 여기 남긴다.**

**앞뒤 여유 페이지가 핵심이다.** "표가 이 페이지에서 끝나는가"를 봐야 부재 주장을 판정할 수 있는데, 결측 코드가 가리키는 페이지만 보면 그걸 구조적으로 못 본다.

### 2-4. ③ 3자 대조 + 검수 패키지 (신규)

산출물: `data/analysis/actions_absence_verification.md` — `actions_review.md`(MQ-911)와 같은 **기계 생성 검수 패키지** 형식.

코드별로 세 진단을 나란히 놓는다:

| model | code | 파서 주장(`_pending_review` 사유) | triage 라벨 | Elice 판독 결과 | 판정 |
|---|---|---|---|---|---|

**판정 4종**:
- `CONFIRMED_ABSENT` — 두 판독기가 모두 "없다". 부재가 **사실로 확정**된다.
- `RECOVERABLE` — Elice 가 조치문을 읽어냈다. 회수 후보 → D99 게이트.
- `DISAGREE` — 파서와 Elice 가 어긋난다. **사람이 볼 곳이다.**
- `INCONCLUSIVE` — 판독 실패·페이지 범위 밖 등.

⚠ **Elice 를 정답지로 취급하지 않는다.** InsuQ 실측 오탈자 사례가 있다(`용어풀이`→`용어풀0`, `바닥면적`→`비닥면적`). 여기서 Elice 의 역할은 정답이 아니라 **독립 2차 판독기**다 — 두 판독기가 같은 답이면 강한 근거, 어긋나면 사람이 볼 지점을 특정해 준다. 이는 P30(2026-08-19 해소)에서 부재 검사에 양성 축을 건 것과 같은 원리다.

**정본 반영 경로**: 이 문서는 정본을 쓰지 않는다. `RECOVERABLE` 판정분은 D99 게이트(`extract_error_codes.write_canonical()` + 사람 승인)를 거쳐야 `error_codes.json` 에 들어간다. 기존 MQ-919 경로를 그대로 쓴다.

## 3. P28 ⓐ — 외부 응답 원본 보관 규약

Elice 캐시가 이 규약의 **첫 구현체**다. 별도 계층을 새로 짓지 않는다.

### 3-1. 규약

- **위치**: `data/raw/external/<source>/<식별자>.json` — `<source>` 는 `elice` · `law` 등
- **git 추적한다.** D60 그대로 — 원본은 파일이 정본, DB 는 조회용 사본. DB 를 지워도 근거가 남아야 한다
- **저장 내용**: 응답 본문 + 최소 메타(`retrieved_at` · `source` · 대상 식별자)
- 🔴 **요청 파라미터·헤더는 저장하지 않는다.** 자격증명 유출 차단(§3-2)

### 3-2. 자격증명 제약 — 이건 실제로 사고가 났던 지점이다

`fetch_laws.py` 의 요청 `params` 에는 `OC`(법제처 인증값)가 들어간다. `_redact()` 가 존재하는 이유가 그것이다. **"요청+응답을 통째로 저장"하는 순진한 설계는 평문 자격증명을 git 추적 파일로 흘린다.**

이 저장소는 정확히 그 문제로 2026-08-13 에 `git filter-repo` 로 히스토리를 재작성했다(커밋 10개 — 기록에는 2개로 적혀 있었으나 실제로 10개였다). `spikes/law_fetch_contract.py ⓚ` 가 추적 파일 내 평문 부재를 단언하고 있다.

따라서 규약은 **응답 본문만 저장**이고, 회귀가 이를 단언한다(§5).

### 3-3. `fetch_laws.py` 소급 적용

`_fetch_with_meta()` 에서 버려지던 `payload` 를 같은 규약으로 보관한다. 실익은 셋: ① 파싱 로직 수정 시 API 재호출 없이 재파싱 ② 개정·정체성 대조 분쟁 시 "그때 무엇이 왔는지" 증거 ③ 조달청 승인 시 바로 쓸 자리.

⚠ **기존 동작을 바꾸지 않는다** — 저장은 부수효과로만 추가하고, `apply_fetch` 의 입력 계약(`fetch_from_api` 반환 dict)은 손대지 않는다.

## 4. 지출 안전장치

InsuQ 의 규율을 그대로 계승한다. 해당 테스트 파일의 서두가 *"테스트의 최우선 목적은 '기능이 되는가'가 아니라 **'실수로 돈이 나가지 않는가'**"* 라고 적고 있다.

1. `allow_purchase=False` 기본 — 캐시 미스 시 네트워크를 안 타고 예외
2. 캐시 우선 — 캐시가 있으면 구매 허용 여부와 무관하게 네트워크를 안 탄다
3. 가격 상수 명시(45원) — 리포트와 어긋나지 않게
4. **테스트는 네트워크를 절대 타지 않는다** — 캐시 히트 시 `_submit_and_wait` 를 monkeypatch 로 폭파시켜 단언
5. 실행 전 고지 — `N페이지 × 45원 = X원` 을 출력하고 진행
6. `ELICE_API_KEY` 부재 시 **지출 전에** 예외
