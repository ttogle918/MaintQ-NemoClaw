## 결정과 맥락

### D136 — A2A 나가는 호출에 차단기를 둔다

- **계기**: 백로그 P35 가 *"`po.py:approve()` 가 실패를 삼키는 정도로만 부분 달성"* 이라고
  적어 뒀는데, **진단이 한 걸음 모자랐다.** `routers/po.py:230` 이 예외를 삼켜서 발주 승인이
  깨지지는 않는다 — 그런데 상대가 죽어 있으면 **승인 한 건마다 10초 타임아웃을 그대로 문다.**
  *실패를 삼키는 것*과 *빨리 실패하는 것*은 다르다.
- **경계 셋**: ⓐ **파트너 단위**로 연다(스킬 단위면 늦게 열린다 — 판정 대상은 "스킬이
  정상인가"가 아니라 "닿는가") ⓑ **«도달 불가»만 센다** — 400·422 는 오히려 차단기를
  **닫는다**(`on_reachable`) ⓒ 상태는 **프로세스 안에만**(업무 사실이 아니라 관측이고,
  DB 에 쓰면 D10 경계에도 걸린다)
- **ⓑ 는 실사고에서 나온 경계다**: 2026-08-24 `assess-loan` 계약 드리프트 때 400 이
  반복됐는데 **같은 파트너의 `request-withdrawal` 은 정상 동작해야 했다.** 이 경계가 없으면
  한 스킬의 계약 오류가 그 파트너의 멀쩡한 다른 스킬까지 막는다.
- **기각**: ① 현행 유지(위 실측으로 기각) ② **재시도 먼저** — 완전히 죽은 상대에게 재시도는
  대기 시간을 **곱한다**(10s→30s). 재시도는 *간헐적* 실패용이고 차단기 위에 얹을 별건이다
  ③ 스킬 단위 ④ DB 저장
- **도입 즉시 드러난 것**: 차단기가 전역 상태라 `test_client.py` 의 전송 실패 테스트 3건이
  차단기를 열어 **뒤따르는 5건이 조용히 다른 예외를 받았다.** `registry().reset()` autouse
  픽스처로 격리 — **전역 상태를 들일 때는 격리 장치를 같은 커밋에 넣는다.**

### A2A 수신 어댑터 — «미착수»가 아니라 «설계상 없음» (D 번호 아님, 사실 확인)

- **계기**: 수신 어댑터(`:9003`)를 구현하려고 A2A_Q 표준 계약을 열었다가
  **만들면 안 되는 것**임을 확인했다.
- **근거**: `A2A_Q/docs/agent_cards/maintq.json` 의 `skills` 가 **빈 배열**이고
  *"MaintQ는 A2A 스킬을 노출하지 않는다 — 요청을 시작하는 client 역할이 기본이다"* 라고
  적혀 있다. 같은 디렉터리의 `finallq.json` 은 **7스킬**, `insuq.json` 은 **6스킬**.
  **비대칭은 결함이 아니라 역할 배정**이다 — 설비 고장이 나야 돈도 보험도 움직이므로
  제조가 시작점이다. 카드가 언급한 유일한 예외(S15)조차 *"MaintQ 가 응답을 받아 FinAllQ 에
  재요청"* 이라 여전히 client 다.
- **문제**: 이 레포와 이력서가 오래 `:9003 ⬜ 수신 어댑터 미착수` 로 적어
  **하지 않기로 한 일을 밀린 일처럼** 보이게 했다. 이 레포가 P34 의 S6·S15·S16 을
  *"미착수가 아니라 데이터 없음"* 으로 닫으며 세운 원칙을 **스스로 어긴 자리**다.
  백로그 A2A 절 머리에 근거와 함께 못박아 다음 세션이 재착수하지 않게 했다.

### S11 `notify-asset-change` — 서명 **뒤**에 온다 (S12 와 정반대)

- **계기**: A2A 실호출이 막힌 상황에서 할 수 있는 것을 찾다가, 계약
  (`schemas/notify-asset-change.json`)이 완전히 명세돼 있고 MaintQ 데이터에 필요한 필드가
  **전부 있어** 지어낼 것이 없음을 확인(D62).
- **핵심 판단**: 계약이 *"설비 처분 **확정**에 따른"* 변경이라 못박으므로 **미서명 draft 로는
  조립하지 않는다.** S12(정산)는 담보를 푸는 수단 자체라 서명보다 **앞서야** 했는데,
  S11 을 같은 자리에서 보내면 **보험사가 아직 일어나지 않은 처분으로 증권을 고친다.**
- **막은 것을 내보내지 않는다**: 미서명·부보 아님·`building_id` 없음·enum 밖 → 전부 400 이고
  `call_skill` 이 **호출조차 되지 않는다**(테스트가 단언). 빈 값을 실어 보내면 수신부가
  `schema_validation_failed` 를 낸다 — `request-withdrawal` 이 `error_code=None` 으로
  정확히 그 400 을 맞은 전례가 있다.
- **되받지 않는다**: 응답으로 MaintQ 상태를 바꾸지 않는다. 발신 6종 중 상태를 바꾸는 것은
  여전히 S12 하나뿐이고, 테스트가 자산 행 불변을 단언한다.
- **S14 는 착수하지 않았다** — 계약이 `risk_before`/`risk_after` 를 **`number`** 로 요구하는데
  MaintQ 는 `LOW/MEDIUM/HIGH` 서열 등급이다. 내부 산식에 점수(3~9)가 있으나 **InsuQ 가 어느
  척도를 기대하는지 계약에 없고**, 응답의 `margin`(±10%)은 정수 3~9 위에서 의미가 서지 않는다
  (10% = 0.6 이라 정수 격자에 안 걸린다). 임의로 정하면 assess-loan 때와 같은 드리프트다.

## 트러블슈팅

### ㉠ 훅 3개 중 2개가 한 번도 돈 적이 없었다

- **증상**: 없었다 — 그게 문제다. 셋 다 `|| exit 0` 이라 실패가 **아무 데도 보이지 않았다.**
- **원인**: PostToolUse `python -m ruff format .` → 시스템 파이썬에 ruff 가 없어 매번
  `No module named ruff`. Stop `python -m pytest eval/` → `eval/` 에 테스트 파일이 **0개**라
  `no tests ran`. **CLAUDE.md 는 "포매터: ruff (PostToolUse 훅으로 자동 실행)" 이라고 적고
  있었다** — 포맷이 유지된 건 훅이 아니라 사람이 `uv run ruff check` 를 돌렸기 때문이다.
- **해결**: `.claude/hooks/lint_edited.py` 신설(편집한 `.py` **하나만** `ruff check --fix`) ·
  Stop → `uv run ruff check data backend mcp_server spikes eval`(**0.23초**, `eval/` 첫 편입).
  **`uv` 를 못 찾으면 stderr 로 알린다** — 원래 훅의 진짜 결함은 ruff 가 없는 것이 아니라
  **없다는 사실이 안 보인 것**이다.
- 🔴 **`ruff format` 은 켜지 않았다.** 재 보니 **189개 중 110개 파일을 재포맷**한다 —
  이 코드베이스는 `ruff format` 으로 포맷된 적이 없고 규약은 사실상 **린터**였다. 그대로 켜면
  기능 3줄 변경에 스타일 500줄이 섞인 diff 가 나온다. 전면 적용은 훅이 아니라 **의도된
  단독 커밋**으로 할 일이다.
- **실증**: exit 0 만으로는 "작동"과 "조용한 무동작"이 구분되지 않아 위반을 심었다 —
  미사용 import 2 + 미사용 변수 1 → **2건 자동 수정 · 1건(F841, unsafe fix) 보고**,
  `eval/` 에 미사용 import → Stop 훅이 **Found 1 error**. 커밋 `2633a64`
- 📌 **이 저장소가 회귀 스위트에 세운 원칙(*"부재 검사에는 생존 앵커를 함께 건다"*)이
  정작 훅에는 적용되지 않은 자리다.**
