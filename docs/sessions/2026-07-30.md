## 트러블슈팅

### ① `judge_hallucination` 무제한 대기 — 실 20문항 1차 시도가 60분+ 멈춤
- **증상**: `run_eval.py --yes` 1차 실행이 60분(문항당 타임아웃 180초 × 20문항 이론상 최대치)을
  넘겨도 결과 없이 멈춤. CPU 사용량이 거의 0으로 정체.
- **원인**: S4형 문항(`expect_not_found`)에서 호출하는 `judge_hallucination()` 이
  `run_item()` 의 `httpx.AsyncClient(timeout=ITEM_TIMEOUT_S)` 보호 범위 **밖에서** 별도로
  `get_client()`(D40, Gemini) 를 직접 호출하는데 여기엔 타임아웃이 전혀 없었다. 실측상 항상
  일어나는 건 아니지만(같은 코드로 이후 정상 응답도 받음) 한 번 걸리면 무한정 멈춘다.
- **해결**: `asyncio.wait_for(judge_hallucination(...), timeout=ITEM_TIMEOUT_S)` 로 감싸고,
  타임아웃 시 `hallucinated=True` 보수적 fail `JudgeVerdict` 반환(환각률 지표를 거짓으로
  부풀리지 않는다는 기존 원칙과 일관). 문항별 진행 로그에 `flush=True` 추가(다음부터 실시간
  관찰 가능 — 이번 1차 시도는 로그가 프로세스 종료 전까지 안 보여 원인 파악이 늦어졌다).
- **커밋**: `8472ae5`

### ② `run_eval.py` 자신이 `.env` 를 로드하지 않음 — S4 문항만 매번 실행 실패
- **증상**: fix①을 적용한 뒤 재실행하니 T01~T18(S1/S2/S3)은 전부 정상 완료(2.7~27.2초)했는데
  T19·T20(S4)만 매번 "환경변수(또는 .env)에 MAINTQ_LLM_MODEL 이(가) 없습니다" 로 즉시 실패.
  스모크(2문항만)로 축소해도 100% 재현.
- **원인**: 메인 채팅 루프의 LLM 호출은 스폰된 백엔드 서브프로세스 안에서 일어나
  `backend/main.py` 의 `load_dotenv(override=False)` 가 적용되지만, `judge_hallucination()`
  은 **`run_eval.py` 자신의 프로세스**에서 `get_client()` 를 직접 호출한다 — 이 프로세스는
  `.env` 를 한 번도 로드한 적이 없어 OS 환경변수에 없는 `MAINTQ_LLM_MODEL` 을 못 찾았다.
  (`GEMINI_API_KEY` 는 이 머신에 OS 레벨로 이미 설정돼 있어 그쪽만 보이지 않아 혼란스러웠다.)
- **디버그 경로**: 별도 포트로 동일한 `_start_server` 로직을 직접 재현해 실제로는 정상
  작동함을 먼저 확인 → 그 결과 "코드는 맞는데 이 실행만 실패"라는 단서로 프로세스 경계
  차이(서브프로세스 vs 드라이버 프로세스)를 짚어냈다.
- **해결**: `eval/run_eval.py` 모듈 상단에 `load_dotenv(ROOT / ".env", override=False)`
  직접 추가.
- **커밋**: `7e5147f`

### ③ `check_permission_403` 이 이벤트 루프 종료 직후 정지 — 2회 연속 재현
- **증상**: 문항 루프(1~20번)가 전부 끝난 뒤(성공이든 실행 실패든) `check_permission_403()`
  단계에서 CPU 정체 상태로 멈춤. 직접 만든 서버에 동일 HTTP 호출(GET pending· POST approve)을
  curl 로 쳐보면 즉시 응답 — 서버는 멀쩡했다.
- **원인 추정**: `_run_all` 이 `asyncio.run()` 으로 이벤트 루프를 닫은 **직후**, 별도 동기
  `httpx.Client` 로 새 연결을 만드는 경로에서 Windows ProactorEventLoop 관련 소켓 이슈로
  추정(같은 세션에서 `WinError 10014`—소켓 페어 생성 시 "잘못된 포인터 주소" 오류—가 다른
  지점에서도 반복 관측됨). 재시도할 때마다 재현돼 순수 우연은 아니라고 판단.
- **해결**: `check_permission_403` 을 `async`/`httpx.AsyncClient` 로 바꾸고, `_run_all` 과
  하나의 `asyncio.run(_run_stage(...))` 호출 안에서 이어서 실행하도록 변경 — 이벤트 루프를
  닫았다 다시 여는 경로 자체를 없앴다.
- **커밋**: `e714541`

### (미해결) `WinError 10014` — Windows 소켓 계층 불안정, 코드 밖 문제
- **증상**: 이 세션에서 프로세스를 여러 차례 강제 종료(`Stop-Process -Force`)한 뒤부터
  `[WinError 10014] 호출에 대한 포인터 인수를 사용하려는 동안 시스템에서 잘못된 포인터 주소를
  감지했습니다` 가 반복 발생 — 새 이벤트 루프 생성 시, 스폰된 uvicorn 서버 기동 시 등 지점을
  가리지 않고 나타남. fix①②③을 전부 적용한 뒤 4차 시도에서도 서버 기동 단계에서 재현.
- **판단**: 코드 문제가 아니라 이 세션 동안 프로세스/소켓 자원이 소진되었거나 손상된 상태로
  추정(장시간 반복 강제 종료의 누적 효과). curl 등 외부 도구로는 서버가 정상 응답하는 순간도
  있어 완전한 시스템 장애는 아니고 간헐적.
- **다음 세션 조치**: 사용자가 터미널(또는 PC) 재시작으로 소켓 상태를 리셋한 뒤 재개하기로 함.
  fix①②③ 은 전부 회귀(`spikes/eval_replay_guard.py` 16건)·dry-run·`get_client()` 단위
  재현으로 검증 완료 — 코드 자체는 재시도 준비 완료 상태.
- **커밋**: 없음(환경 문제, 코드 변경 대상 아님)
