## 결정과 맥락

### D126 — 결재 상태 전이는 행을 잠근 채 판정한다

- **계기**: 세 서비스(`po`·`decisions`·`repairs`)의 전이 함수가 앞 네 단계를 글자까지 똑같이
  반복하는 것을 보다가, 그 공통 골격에 `FOR UPDATE` 가 **없다**는 것을 발견. 격리 스키마에서
  두 결재자의 동시 승인/반려를 재현하니 **둘 다 200** 이 나왔고 한쪽 결재가 흔적 없이 사라졌다
  (승자가 실행마다 바뀜 = 비결정적 경쟁의 증거).
- **왜 안 잡혔나**: `spikes/db_concurrency.py` 는 **서로 다른 테이블에 대한 INSERT** 끼리만 봤다.
  *"같은 행에 대한 두 전이"* 를 세우는 검사가 34스위트 어디에도 없었고, 단일 요청 계약
  (`api_contract` 52건 등)은 요청을 **하나씩** 보내므로 전부 통과했다.
- **이름이 사고를 가렸다**: `decisions`·`repairs` 의 헬퍼는 `_locked_row()` 라는 이름을 달고도
  평범한 SELECT 였다. 이름이 거짓이면 호출부는 안전하다고 *믿고* 검토를 건너뛴다.
- **대안과 기각 사유**:
  - *격리수준을 SERIALIZABLE 로* — 직렬화 실패(40001) 재시도 배선이 없고, 결재와 무관한
    조회까지 비용을 문다
  - *낙관적 잠금(`If-Match`)* — 사용자에게 "누가 먼저 눌렀다"를 보여줄 수 있어 더 낫지만
    스키마 + API 계약 변경이 따른다. 409 로도 안전은 확보되므로 백로그로
  - *상태 기계 전체를 합치기* — `decisions.sign()` 의 6단계 순서 계약(D84)과 `repairs.sign()`
    의 해시 산출은 **의도적으로 다른 로직**이라 하나의 추상 아래 넣으면 계약이 흐려진다.
    그래서 **골격만** 공통화했다(사용자와 합의한 범위)

### D127 — 커넥션 풀, 단 격리 DSN 은 제외

- **계기**: `get_po()` 가 커넥션을 2개, 전이가 3개 여는 것을 계측하다 **커넥션 1개에 ~16ms**
  (핫 쿼리는 0.03~0.8ms)라는 걸 확인.
- **더 큰 이유는 안정성이었다**: 회귀를 병렬로 돌리다 Windows TIME_WAIT 소켓이 **933개**까지
  쌓여 Docker 포트 프록시가 죽고 호스트에서 DB 접속이 통째로 끊겼다. 매 쿼리마다 새 TCP 를
  여는 구조가 부하에서 **환경을 멈춰 세웠다**.
- **핵심 안전 규칙**: 스파이크는 실행마다 새 격리 스키마 DSN 을 만든다. 그걸 풀에 넣으면
  스키마 수만큼 풀이 쌓여 커넥션을 고갈시킨다 → **기본 대상일 때만** 풀을 태운다.
- **대안 기각**: *요청 스코프 커넥션(Depends)* 은 서비스 30여 곳의 `db_path` 시그니처를 전부
  손대야 한다. 풀은 그 시그니처를 **한 글자도 바꾸지 않고** 같은 이득을 준다.

### D128 — 도구 호출은 직렬로 둔다 (구현하지 않음)

- **계기**: 리뷰에서 "MCP 직렬화가 병목"으로 지목. 실측해 보니 **진단이 절반 틀렸다.**
- 직렬 지점이 둘인데 성격이 다르다 — ① 루프의 순차 dispatch(`for tu in pending:`) ② 워커의
  큐 직렬 소비. **②만 고치면 이득이 0** 이다(①이 결과를 기다리므로 워커에 동시 요청이 애초에
  없다). ②가 무는 것은 동시 사용자뿐이고 현 스코프는 단일 사용자 데모.
- ①(진짜 이득)은 **선행 계약 변경**이 있다. `traces` 에 pair 키가 없어 프론트 매퍼가
  *"같은 tool 의 가장 이른 미완료 call"* 과 짝짓는데, 그 근거가 ①의 순차성이다.
  `frontend/lib/trace.ts` 주석이 이 리팩터를 **정확히 예견해 뒀다** — *"병렬 호출로 바뀌면
  이 매퍼가 조용히 잘못 짝짓는다."* 실패가 아니라 **틀린 감사 화면**이 나오고, `traces` 는
  평가 판정 소스라(D21·D30) 지표까지 오염된다.

### D129 — 타입 힌트 정합화

- **계기**: Postgres 전환(D116) 이후에도 시그니처가 `sqlite3.Connection` 이었다. 런타임에
  그런 객체는 오지 않는다. **틀린 힌트가 없는 힌트보다 해롭다** — 이 레포는 SQLite/Postgres
  혼동으로 이미 여러 번 사고를 냈고 그때마다 "이게 무슨 커넥션인지"가 쟁점이었다.
- **대안 기각**: *mypy 도입 후 정식 타이핑* 은 규모가 다르다(타입 체커 없는 레포에 88곳).
  지금 필요한 건 *"힌트가 사실과 맞을 것"* 뿐이다.

### D130 — 애플리케이션 런타임은 Postgres 전용, 폴백은 큰 소리로 실패

- **계기**: 사용자의 지적 — *"우리 SQLite 말고 PostgreSQL 쓰기로 한 거 아니었어? 그러면
  관련 내용들을 모두 수정해야 할 것 같은데 그건 버그로 안 치는 거야?"*
  처음 리뷰에서 나는 이걸 *"발견했지만 손대지 않은 것"* 으로 약하게 적었다. **지적이 맞았다** —
  조사해 보니 버그 3건이었다.
- **경계를 그은 것이 이 결정의 핵심**: SQLite 를 전부 지우면 스파이크 20개가 죽는다
  (`rules_db_load` 는 무결성 게이트를 SQLite 픽스처로 흔든다). `sqlite3.Error` 예외 40곳도
  정상이다(`dbcompat._map_exception` 이 psycopg 예외를 그 타입으로 되던지는 설계).
  → **런타임의 조용한 폴백은 버그, 픽스처용 SQLite 는 기능.**

## 트러블슈팅

### ㉠ 두 결재자의 동시 승인이 둘 다 200 (D126)
- **원인**: Postgres READ COMMITTED 에서 UPDATE 대기가 풀리면 WHERE 절을 재평가하는데
  그 절에 `state` 조건이 없어 항상 매칭된다. 전이 판정은 SELECT 시점에 한 번 하고 버려졌다.
- **해결**: `txn.locked_row()` = `SELECT ... FOR UPDATE`. 커밋 `a8c1d78`

### ㉡ 평가가 0행 위에서 지표를 계산 (D130, 영향 최대)
- **증상**: `eval/run_eval.py` 가 `data/maintq.db`(SQLite)를 복사해 자식 서버에 `MAINTQ_DB` 로
  넘겼다.
- **원인**: **Postgres 백엔드는 `MAINTQ_DB` 를 읽지 않는다.** 자식은 상속받은 `DATABASE_URL` 로
  **공유 public** 에 traces 를 쓰고, 스크립트는 아무도 쓰지 않은 SQLite 사본을 읽었다.
  평가가 조용히 무의미해지면서 동시에 실 데이터를 오염시켰다 — **M4 헤드라인 지표(환각률)가
  이 위에 있었다.**
- **해결**: `pg_isolation.create_isolated_schema()` 로 이관. 커밋 `98b9200`

### ㉢ CLAUDE.md 가 원인을 잘못 짚고 있던 오염 (D130)
- **증상**: `a2a_partner_tools_contract ⑤-a` 가 `count=4` 로 떨어짐. 문서는 *"이 브랜치와
  무관한 기존 오염"* 으로 적고 원인을 다른 곳에서 찾고 있었다.
- **원인**: **그 스파이크 자신**이 실행마다 `public.traces` 에 6행을 썼다(실측 0 → 6).
- **해결**: 격리 스키마로 전환. 22건 유지 · `traces` 0 → 0. 커밋 `98b9200`

### ㉣ 환경변수 하나가 빠지면 두 모듈이 다른 DB (D130)
- **원인**: `DATABASE_URL` 부재 시 `dbcompat` → SQLite, `backend/db.py` → `localhost:5432`
  (무응답 → 무한 대기). **둘 다 침묵.**
- **해결**: 기본값 제거 + `DatabaseUrlMissing`(고치는 법을 메시지에). 커밋 `98b9200`

### ㉤ 🔴 내가 D129 에서 회귀 하나를 죽였다
- **증상**: `law_fetch_contract` 28건이 `ModuleNotFoundError: No module named 'data'` 로 사망.
- **원인**: `data/rules/engine.py` 에 런타임 `from data.dbcompat import` 를 넣었는데, 이 모듈은
  `import engine` 으로 **독립 임포트**되는 경로가 있다(`fetch_laws.py`·그 스파이크가 `sys.path`
  에 `data/rules` 만 넣고 연다).
- **해결**: `if TYPE_CHECKING:` 가드. 커밋 `6119970`
- ⚠ **D129 커밋 당시 이 스파이크를 안 돌렸다** — 그때 13종만 검증했다. 부분 검증의 한계.
