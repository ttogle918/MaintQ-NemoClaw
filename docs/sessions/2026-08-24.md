## 트러블슈팅

### `backend.main:app` 라이브 서버가 모든 DB 엔드포인트에서 hang
- **증상**: `uv run uvicorn backend.main:app --port 8003`을 몇 번을 재시작해도 `/api/po` 같은
  DB 조회 엔드포인트가 응답 없이 멈춘다. `/health`는 정상 응답.
- **시도하고 배제한 원인들**: 특정 라우터(po/chat/a2a/전체 13종 각각 재현·재현 안 됨 혼재) ·
  MCP 서브프로세스(끈 채로도 재현) · CORS 미들웨어 · `DATABASE_URL`의 `localhost` vs `127.0.0.1`
  (둘 다 직접 psycopg 로는 즉시 연결됨) · Docker 컨테이너 재시작 · Postgres 커넥션/락(`pg_stat_
  activity` 조회 시 아무것도 안 잡힘) · 포트 번호(8003/8004/8006/8008/8009/8010 전부 재현) ·
  파일명(동일 내용을 다른 이름으로 복사해도 재현) · 잔존 프로세스·`.pyc` 캐시(전부 정리해도 재현)
- **부분적 실마리**: 세션 후반, 로컬에서 병행 진행 중이던 다른 Claude 세션(FinAllQ 쪽 A2A 검증)이
  같은 타이밍에 같은 `backend.main:app`(8003)·같은 Postgres(5434)를 실제로 쓰고 있었다는 것을
  cross-session 메시지로 확인했다 — 이게 상당 부분의 hang을 설명할 개연성이 높다(같은 시간대에
  격리 스키마 회귀 스파이크도 같은 증상으로 멈춤). **다만 그 세션이 8003을 완전히 내린 뒤에도
  똑같은 증상이 재현**돼서, 동시 접근이 유일한 원인은 아니었던 것으로 보인다.
- **해결**: 근본 원인은 끝내 찾지 못했다. 코드 정확성은 `get_po()` 등을 직접 함수로 호출하거나
  `spikes/api_contract.py`(격리 Postgres 스키마 + `TestClient`, 실 네트워크 소켓을 안 씀)로
  대체 검증했다 — 둘 다 매번 정상 통과했다.
- **다음 세션 확인 사항**: 라이브 서버가 여전히 hang하면 머신 재부팅을 시도해 볼 것(프로세스·
  컨테이너 재시작으로는 해소 안 됨을 이미 확인). 재현되면 `spikes/`에 이 패턴을 잡는 회귀를
  추가할지 검토(현재는 우연히 아무 스파이크도 이 경로를 실 HTTP 서버로 때리지 않아서 회귀
  스위트 자체는 전부 정상 통과하고 있다 — **회귀가 통과해도 라이브 서버가 죽어 있을 수 있다는
  뜻**이라 이 자체가 하나의 갭이다).
- **관련 커밋**: `dcf538b`(A2A 버그 자체는 무관하게 해결·검증됨), `45b5040`·`2cccdd3`·`63a82f0`
