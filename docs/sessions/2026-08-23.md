## 의논 내용과 결정 맥락

- **착수 시점 막힘**: "다른 세션이 SQLite→Postgres 마이그레이션 중"이라는 전제로 시작했으나, 실제로는 "코드만 전환되고 접속 가능한 Postgres 가 없는" 상태였다. 사용자에게 확인 후 **로컬 Postgres 직접 띄우고 마이그레이션을 이 세션에서 마저 완성**하기로 범위 확대(원 계획 문서 자체가 "2-3주" 로 추정했던 작업).
- **DDL 변환 방식**: 사용자가 "정규식으로 변환 가능한 건 정규식으로" 명시적으로 지시 — `scripts/convert_ddl.py` 를 손패치가 아니라 체계적 정규식 함수들로 확장(datetime·boolean·`IS`→`IS NOT DISTINCT FROM`·예약어).
- **호환 계층 방식**: 사용자가 "변환 패키지 있다던데" 제안 → 기성 패키지 대신 자체 sqlite3-호환 shim(`data/dbcompat.py`)을 만들기로 결정. 기존 코드(`?` 플레이스홀더, `sqlite3.IntegrityError`, `PRAGMA`)를 거의 그대로 재사용할 수 있어 45개 SQLite 결합 파일 각각을 손으로 재작성하는 것보다 훨씬 적은 변경으로 끝났다.
- **스파이크 격리 전략**: "스파이크마다 임시 Postgres 스키마 생성" 방식을 사용자가 승인 — `data/pg_isolation.py` 로 구현. SQLite 시절 "파일 전체 복사" 격리의 직접적 대체물.
- **`bundle_integrity.py` skip 결정**: 이 스파이크는 픽스처 DB 변형 7종이 전부 `sqlite3.connect()` 에 직결돼 있어 다른 스파이크보다 포팅 규모가 훨씬 컸다. 사용자에게 "데이터 SQL 은 이미 다 변환된 거 맞나"라고 확인받음 — 맞다(앱 스키마·마이그레이션 자체는 이미 완성, 이 스파이크의 gap 은 **테스트 파일 자체의 픽스처 코드**가 아직 sqlite3 를 직접 쓴다는 것뿐), 그 전제 위에서 skip 승인.
- **커밋·push**: 대규모 diff(37파일)였고 다른 세션이 이미 이 브랜치(master)에 마이그레이션 커밋을 여러 개 쌓아 온 선례가 있어, 사용자에게 명시적으로 커밋/push 여부를 확인 후 진행.

## 트러블슈팅

### `s10_smoke.py`·`sp3_sse_events.py` 가 공유 Postgres `public` 스키마를 오염시킴
- **원인**: 두 스파이크 모두 실 uvicorn/MCP stdio 서브프로세스를 띄우면서 자식 env 에 `MAINTQ_DB`(SQLite 시절 변수)만 넘겼다. `backend/db.py`·`mcp_server/db.py` 는 Postgres 전용으로 바뀌며 `MAINTQ_DB` 를 더 이상 읽지 않고 `DATABASE_URL`(공유 DB)로 폴백한다 — 자식이 "격리된 척" 하면서 실제로는 공유 스키마에 썼다.
- **해결**: `pg_isolation.create_isolated_schema()` 로 만든 DSN 을 자식 env 의 `DATABASE_URL` 로 직접 주입(`MAINTQ_DB` 대신). `data/seed.py --with-error-codes` 로 오염된 행 정리(전체 스키마 재생성이라 완전히 청소됨).
- **커밋**: `ba4fb96`

### `dbcompat._BOOL_COMPARE` 가 `<>`/`!=` 를 처리 못 함
- **원인**: boolean 컬럼 리터럴 비교 정규식이 `col = 0/1` 형태만 잡고 있어, `override <> 1` 같은 SQLite 스타일 쿼리가 Postgres 에서 `operator does not exist: boolean <> integer` 로 죽었다.
- **해결**: 정규식을 `=`·`<>`·`!=` 3종 다 잡도록 확장. 여러 스파이크(`disposal_sign_contract.py` 등)에 공통으로 영향 — 시스템 차원 수정 하나로 여러 개별 실패가 함께 풀렸다.
- **커밋**: `ba4fb96`

### `disposal_sign_contract.py`·`approvals_contract.py` 의 mutant-table CHECK 검증이 Postgres 에서 불가능해 보였음
- **원인**: `SELECT sql FROM sqlite_master` 로 원본 DDL 텍스트를 얻어 CHECK 절을 정규식으로 도려내는 SQLite 전용 기법. Postgres 에는 `sqlite_master` 자체가 없다.
- **해결**: `CREATE TABLE decisions_mutant (LIKE decisions INCLUDING ALL)` 로 제약까지 포함해 복제한 뒤, `pg_get_constraintdef()` 로 대상 CHECK 만 이름을 찾아 `DROP CONSTRAINT`. Postgres 가 `IN (...)` 을 `= ANY (ARRAY[...])` 로 재구성해 렌더링하는 것도 실측으로 확인해 마커 상수를 이원화(`CHECK_BLOCKING_OVERRIDE_PG`).
- **커밋**: `ba4fb96`
