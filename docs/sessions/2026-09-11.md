## 결정과 맥락

### D138 — S13 payload 에 «원가»를 싣는다

- **계기**: FinAllQ 어댑터를 띄워 S13 을 태웠더니 **금액과 무관하게 항상**
  `COLLATERAL_INSUFFICIENT` 였다. 같은 자산에 3,000,000 신청 → 감정가 1,500,000,
  1,000,000 신청 → 500,000. **비율이 0.5 로 고정**이었다.
- **원인**: FinAllQ 는 `inspection_data.original_cost` 가 없으면 원가를 **`loan_amount` 로
  대체**한다(그쪽 코드 주석이 "보수적 근사치"라고 적어 둔 폴백). 그러면 감정가 =
  신청액 × 잔존율(<1) 이라 **언제나 신청액보다 작아 승인이 구조적으로 불가능**하다.
  셋 다(계약에 원가 필드 없음 · 폴백 · REJECTED 면 InsuQ 미호출) 개별로는 합리적인데
  맞물려서 **2차 홉이 영원히 안 열린다.**
- **우리가 그 값을 갖고 있었다**: `assets.acquisition_cost`(9자산 중 8건). 지어내는 게 아니다.
- **기각**: ② `appraised_value` 에 `book_value` — 그 키는 상대의 감가상각을 **통째로
  건너뛰는 override** 이고 장부가액은 회계 수치이지 감정가가 아니다(D62·D74). ③ 계약 개정
  대기 — `inspection_data` 는 자유 객체이고 상대가 **그 키를 이미 읽는다**. ④ `loan_amount`
  조정 — 신청액은 사람이 정하는 값이라 흔들면 요청 자체가 거짓이 된다.
- ⚠️ **원가를 실어도 못 여는 자리**: 취득 16년차(내용연수 8년 초과) 자산은 잔존율 0 →
  백엔드 400. 그건 그쪽 감가상각 산식이고 payload 로 우회할 자리가 아니다.

### D139 — 차단기는 «전송계층 실패»만 센다

- **계기**: D136 차단기를 **실제 파트너로** 검증하다가(어댑터를 죽였다 살리며 전이 관찰)
  **기준선 호출이 502** 인 것을 보고 파헤쳤다. FinAllQ 가 죽어서가 아니라
  **FinAllQ→InsuQ 2차 홉**이 실패한 것이었다.
- **문제**: trace 에 두 종류가 나란히 남는다 — `Cannot connect to A2A adapter at ...`(상대가
  죽음)와 `A2A adapter finallq returned 502`(상대는 살아 있고 그 뒤가 죽음). **둘을 같이 세면
  InsuQ 장애 3회에 `finallq` 차단기가 열려 InsuQ 와 무관한 S5·S12 까지 막힌다** —
  D136 이 경계 ⓑ 로 막으려던 병리가 **2차 홉이라는 다른 층에서 재발**했다.
- 📌 **코드가 이미 그 원칙을 문장으로 적고 있었다** — *"여기 아래는 전부 «상대가 응답을
  돌려줬다» = 살아 있다는 증거다"* 주석 **바로 위**에 그것을 어기는 블록이 있었고, 그 블록의
  주석조차 *"어댑터는 **떴는데**"* 라고 상대가 살아 있음을 인정하면서 도달 불가로 셌다.
- **기각**: ② 응답 본문의 `hop`·`cause` 로 판정 — 부가 필드라 계약 보장이 없고, **사라지면
  신호가 조용히 증발**한다. 반면 «응답을 받았다»는 신호는 사라질 수가 없다(응답을 받는 것이
  곧 신호다). ③ 5xx 를 예외 목록에 추가 — 목록은 다음 상태코드에서 또 빠뜨린다. **축을 바꾸는
  것**이 맞다. ④ 스킬 단위 차단기 — 지금 불필요.
- ⚠️ **비용이 큰 경우는 덮인다**: 아플 만큼 느리면 **우리 타임아웃이 먼저** 걸려 정상적으로
  열린다(응답이 **없으므로**). 상대의 504(판단해 보낸 **응답**)와 우리 타임아웃(**응답 없음**)은
  다른 사건이라 회귀로 따로 못박았다.
- 🔴 **한계**: 상대가 자기 사정으로 계속 500 을 뱉으면 안 열린다. HTTP 응답은 **스킬 단위
  결과**이지 파트너 건강 신호가 아니므로 다루려면 스킬 단위 백오프가 맞는 자리다.

### D140 — S13 트리거는 화면이 아니라 MCP 도구

- **계기**: FinAllQ 세션이 3연결 데모 영상을 위해 *"MaintQ 에 A2A 트리거 버튼이 있나"* 를
  물었다. 프론트를 전수 확인하니 `/api/a2a/*` 로 나가는 **POST 는 0건**이었다.
- 🔴 **그런데 결론이 달랐다** — S8 도, 약관조회도, S12 도 **프론트에서 부르지 않는다.**
  트리거 층이 **MCP 도구**다. 즉 *"S13 에 트리거가 없다"* 는 **UI 결손이 아니라 도구
  카탈로그의 빈칸**이었다(A2A_Q 세션이 짚었고, 실측으로 확인했다).
- **기각**: ①·② 화면 신설 — 폼·응답 렌더·`lib/` 순수 함수·`ui_honesty` 6~12건이 따라오는데
  도구는 100행짜리 형제 파일 하나다(엔드포인트는 이미 있다). **기존 GIF 01·03 이
  *"챗에서 물으면 A2A 가 돈다"* 문법을 세워 놨고 S13 만 버튼이면 그 문법이 깨진다.**
  ④ 형제처럼 5xx 뭉개기 — **오늘 D139 로 푼 것을 도로 합치는 것**이다.
- **경계 셋**: ⓐ 원가를 파라미터로 두지 않는다(두면 LLM 이 지어낼 자리가 생긴다)
  ⓑ DESCRIPTION 이 **«승인» 표현을 금지**한다 — `decision:"approved"` 는 담보 조건 충족
  판정이고 상대 장부는 심사중으로 남는다 ⓒ **503(차단기)을 502·504 와 분리**한다.

### D141 — S11 통지에 멱등키를 싣는다

- **계기**: S11 이 우리 엔드포인트로는 400 `idempotency_key_required` 에서 막혀 있었다.
  그런데 그 헤더가 **계약면(`schemas/`·`agent_cards/`)에 0건**이라 처음엔 «계약 없이
  구현하지 않는다»로 대기했다(사용자 결정).
- **대기를 푼 근거**: A2A_Q 세션의 구분이 결정적이었다 — 계약 공백이 «동작을 **모르는**
  상태»가 아니라 **«동작은 아는데 적힌 자리가 없는 상태»** 였다. 상대 의미론을 **배포된
  구현으로 공개**받았다(3중 복합키 `(requester, skill_id, key)` · 같은 payload SHA-256 →
  재생 · 다르면 409 · 128자). 계약이 서도 이 파생은 달라지지 않는다.
- ⚠️ **구현이 CP-006 을 대체하지 않는다** — 이건 «이 헤더 하나»를 푸는 것이고, CP-006 이
  푸는 것은 **헤더 요구사항을 적을 자리가 계약에 없다**는 구조적 공백이다
  (`X-Request-Chain-Id` 도 계약면 0건인데 양쪽이 우연히 수렴했다).
- **기각**: ② 난수·UUID — 재전송이 다른 키가 되면 **멱등성이 성립하지 않는다**
  ③ `request_chain_id` 재사용 — 호출마다 새로 나므로 재전송에서 달라진다(상관관계 키이지
  동일성 키가 아니다) ④ 클라이언트가 전 스킬에 자동 부착 — 클라이언트는 «무엇이 같은
  요청인가»를 알 수 없어 **키를 만들 자격이 없다.** 호출자가 넘긴다.
- 🔵 **`change_type` 을 반드시 넣는다** — 같은 결정이라도 REMOVE 와 ADD 는 다른 통지이고,
  키가 같으면 뒤엣것이 **재생으로 처리돼 조용히 사라진다.** 128자 초과 시 앞을 자르되
  `change_type` 은 **뒤에 두어 살린다**(REMOVE/ADD 혼동이 길이 초과보다 나쁘다).

## 트러블슈팅

### ㉠ InsuQ `equipment` 계약 드리프트 — 실호출로만 잡히는 결함

- **증상**: S11 발신이 400. 본문은 `{"detail":"request body must be a JSON object"}`.
- **오진 유도**: 그 문구는 **사실이 아니었다**(우리가 보낸 건 JSON object 가 맞다). 그래서
  처음엔 우리 payload 조립을 의심했고 **한글 인코딩까지** 파봤다(ASCII·raw UTF-8·`\uXXXX`
  세 형태가 **전부 동일하게 실패**해서 인코딩을 배제).
- **해결 경로**: 필드를 **하나씩만 담아** 보내 파싱/검증 경계를 갈랐다 — 7필드는 파싱되고
  `equipment` 만 실패. 모양별로 `["WRAP"]`🔴 `"WRAP"`🔴 `[1]`🔴 **`[{"name":"WRAP"}]`✅** `[]`✅.
- **판정**: 계약은 `array<string>` 이고 **InsuQ DTO 가 `array<object>`** 였다. 2026-08-24
  `assess-loan` 선례대로 **우리 payload 를 바꾸지 않았다.** InsuQ 가 수정·배포(`296a4f6`).
- 📌 그쪽 진단 문구도 함께 고쳤다 — 이제 Jackson 원인 필드를 짚는다.

### ㉤ 409 를 실물로 봤다 — 내가 만든 충돌이었다

- **증상**: D141 을 붙이고 첫 호출이 **409 `idempotency_conflict`** —
  *"Idempotency-Key 'DEC-0001:REMOVE' was already used with a different request body"*.
- **원인**: **내 어제 수동 probe** 다. 같은 키를 `BLD-A`/`SB-2023-0001` body 로 이미 썼는데,
  **재시드로 `decision_id` 시퀀스가 리셋**되면서 `DEC-0001` 이 재사용돼 부딪혔다.
- **해결**: 새 결정(`DEC-0002`)으로 태우니 200. 코드 문제가 아니다.
- 📌 **의도한 실험은 아니었지만 값이 있다** — 멱등성은 성공 경로보다 **충돌 경로가 도는 것**을
  봐야 증명되는 축이다. 「같은 키 + 다른 내용은 막는다」가 실물에서 동작했다.
- ⚠️ **재시드가 시퀀스를 되돌린다는 것**은 다음에도 물릴 수 있는 함정이다 — 외부 저장소는
  우리 재시드를 모른다. 실호출 검증 뒤 재시드하면 **같은 id 가 다른 내용으로 다시 나간다.**
