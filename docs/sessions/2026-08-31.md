- **결론**: 가설적 위험을 막으려고 회귀 전체를 한 줄에 인질로 잡는 거래다. 하지 않는다

## 트러블슈팅

이번 세션의 본체다. **연결 장애 3건이 연달아 났고 셋 다 원인이 달랐다.**

### ① `lookup-clause` 502 → 401 → 200 (세 단계, 세 원인)

- **502**: 코드 기본값이 `:9102`(InsuQ 가 삭제한 FastAPI 어댑터)를 보고 있었다.
  8-30 에 `:8081` 로 고쳤다 — **커밋 `d4e6618`**
- **401**: 그런데 그 수정이 **한 번도 효과를 낸 적이 없었다.** `.env:48` 이
  `MAINTQ_A2A_INSUQ_BASE_URL=http://localhost:9102` 로 **코드 기본값을 덮고 있었다**(D56 —
  OS env·`.env` 가 코드보다 우선). `.env` 를 `:8081` 로 고쳐 해소
- **또 401**: 토큰이 맞는데도 거부됐다. 사용자가 "값은 똑같은데"라고 했고 **그 말이 맞았다** —
  두 파일의 값이 **sha256 까지 동일**했다. 문제는 값이 아니라 **전달 경로**였다:
  `A2A_MOCK_TOKEN` 이 `InsuQ/ai-engine/.env`(파이썬 dotenv 전용)에만 있었고 **Spring(Java)은
  그 파일을 읽지 않는다.** 게다가 `:8081` 프로세스는 8-30 10:39 기동이라 **무엇을 넣었든 다시
  뜬 적이 없어 못 읽었다.** compose 의 `backend` 서비스가 읽는 `InsuQ/backend/.env` 를
  신설해 해소(그 파일은 **아예 존재하지 않았다**)

### ② 화면이 백엔드에 연결 못 함 (503)

- **증상**: 프론트가 `:8897` 을 부르는데 백엔드는 `:8000` 에 있었다
- **원인**: `frontend/.env.local` 이 `NEXT_PUBLIC_API_BASE=http://localhost:8897` 로,
  **도커 판 백엔드를 전제**한 리허설 구성이었다(`docker-compose.override.yml` 의 `8897:8000`)
- **해결**: 백엔드를 `:8897` 로 이동(**설정 파일 0개 수정**). 도커로 올리는 안은 기각했다 —
  그 override 에 `MAINTQ_A2A_INSUQ_BASE_URL: :9102` 가 박혀 있어 **①에서 푼 문제가 되돌아간다**
- CORS 는 문제없었다 — `backend/main.py:94` 가 `DEV_PORTS = range(3000, 3006)` 으로 **범위**를
  열어둔다("포트를 하나로 박으면 다른 프로젝트에 물릴 때 막힌다"는 설계 의도)

### ③ 화면에서 `search_insurance_clause` 연결 거부 (WinError 10061) ← **내가 만든 것**

- **원인**: MCP 도구는 InsuQ 를 직접 부르지 않는다 —
  `mcp_server/tools/search_insurance_clause.py:23` 이 `_DEFAULT_BASE_URL = "http://localhost:8000"`
  으로 **MaintQ 자기 백엔드**를 부른다. ②에서 백엔드를 `:8897` 로 옮기며 **그 주소를 비웠다.**
  연결 거부는 InsuQ 가 아니라 **MaintQ 가 자기 자신에게 못 닿은 것**이었다
- **해결**: `MAINTQ_BACKEND_BASE_URL=http://localhost:8897` 명시 후 재기동
- ⚠️ **교훈**: `:8000` 이 비었다고 경고까지 해놓고 그 경고가 **내 자신의 MCP 도구에도 해당된다는
  걸 놓쳤다.** 게다가 검증을 `curl` 로 REST 만 해서 200 을 받고 "확인됐다"고 보고했는데, 그건
  **MCP 도구를 건너뛴 다른 경로**였다. 화면 경로(채팅)로 안 봐서 촬영 중에 발견되게 만들었다.
  **스택 구성을 바꾸면 REST 가 아니라 화면 경로로 검증할 것**

### ④ 스파이크 2건 FAIL — 내 E2E 가 공유 DB 를 오염

- **증상**: `write_tool_contract ⑱·⑳` 이 `verdict_at_signing` 을 `BLOCKED` 대신 `CONDITIONAL` 로 받음
- **원인**: S12 E2E 가 `AST-L3-CONV.lien_consent_ref` 를 채워 담보 차단이 풀렸고, 스파이크가
  격리 스키마를 만들 때 그 `public` 데이터를 **복제**했다. 코드 결함이 아니다
- **해결**: 재시드(사용자 승인 후). 30/30 복구
- ⚠️ **공유 DB 를 건드리는 실행은 사전에 알릴 것** — 다른 세션이 촬영 상태를 기다리고 있었다
