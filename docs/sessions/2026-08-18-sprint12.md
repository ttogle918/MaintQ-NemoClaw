## 의논 내용과 결정 맥락

### PM이 계획 파일을 안 쓰는 문제가 이번에도 재발

Sprint 11 계획 확정 때 PM 에이전트가 최종 계획 텍스트는 완성했지만 `Write`로 실제 파일을 만들지 않는
일이 있었다. 이번 Sprint 12에서도 동일하게 재발(PM 응답에 파일 경로 언급은 있었지만 실제
`docs/sprints/sprint-12.md`가 디스크에 없었음). 원인 진단 없이 오케스트레이터가 즉시 직접
`Write`로 파일을 작성해 처리 — 매번 PM 산출물이 실제로 디스크에 반영됐는지 확인하는 습관이 필요하다는
교훈이 다시 확인됨.

### `sprint-12-s29-ui`라는 새 브랜치를 만든 이유

Sprint 11 종료 후 `master`에 병합·푸시가 끝난 상태였다. Sprint 12 스테이지 작업을 `master`에 바로
커밋하지 않고 새 브랜치를 판 것은 이 프로젝트의 확립된 관행("브랜치 작업 · 머지는 요청 시에만")을
그대로 따른 것 — 스프린트가 끝나도 자동으로 `master`에 합치지 않는다.

### 산출 등급·저장 등급 UI 문구가 오해를 산 지점

사용자가 "긴급/일반"·"pending/approved"로 추측했다는 건 두 값이 **다른 종류의 정보**(우선순위·승인
상태)로 보일 수 있다는 신호다. 실제로는 둘 다 위험등급(LOW/MEDIUM/HIGH)이고 측정 **시점**만 다르다.
당장 화면 설명을 추가하지는 않기로 했지만, 후속 스프린트에서 UI 카피를 다듬을 후보로 남을 만하다
(세션 로그에만 기록, 백로그 등재는 안 함 — 사용자가 명시적으로 미루기로 했으므로).
