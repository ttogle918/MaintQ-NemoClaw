## ① INV-L3-01 + OCT 는 쓰지 말 것 — 반복고장 HOLD 함정

원래 큐시트가 계획했던 조합(INV-L3-01, OCT)은 seed 데이터에 **최근 30일 내 3회** 발생
이력이 이미 들어 있어서, 진단 즉시 "반복 고장 감지" 배지가 뜨고 `create_po_draft`가
**HOLD**(발주 보류 — 원인 확정 후 진행)로 막힌다. 안전 경고·반복고장 배지 자체는 데모
포인트로 괜찮지만, 그 다음 "점검 결과 입력" 버튼을 눌러도 **아무 반응이 없다**(모달도
안 뜨고, 채팅 입력창에 프리필도 안 됨) — 코드 확인 결과 `frontend/components/...`(정확한
컴포넌트는 다음 세션에서 추적) 쪽에 클릭 핸들러가 없거나 죽어 있는 것으로 보인다. **아직
고치지 않았다** — 사용자가 "이번엔 pass, 나중에 하나씩 잡자"고 결정.

채팅으로 프리텍스트("근본원인은 OO로 확인되었고 교체가 필요합니다")를 직접 타이핑해서
우회를 시도해봤지만, **정확한 부품명(모터 출력 케이블)을 넣어도 여전히 HOLD였다** — 즉
이 게이트는 자연어 설명으로는 안 풀리고 오직 "점검 결과 입력" UI 플로우로만 풀리게
설계된 것 같다. 그 UI가 죽어 있으니 **INV-L3-01+OCT는 현재 완전히 막다른 골목**이다.

**우회책**: DB에서 반복고장 이력이 없는 조합을 직접 확인했다 —

```sql
SELECT equipment_id, code, count(*) FROM error_history
WHERE occurred_at >= (CURRENT_DATE - INTERVAL '30 days')
GROUP BY equipment_id, code ORDER BY count(*) ASC;
```

INV-L3-02(같은 iG5A)는 OCT가 최근 30일 1건뿐이라 반복고장으로 안 잡힌다. 같은 에러코드라
매뉴얼 인용·안전 경고 대사는 거의 그대로 재사용할 수 있으면서 3턴 안에 깔끔하게
발주까지 끝난다 — 큐시트를 이걸로 갱신해 뒀다.

## ② 부품명을 지어내지 말 것

첫 시도에서 임의로 "충격 암친서 26"이라는 가짜 부품명을 넣었더니, LLM이 그럴듯한 재고
조회(`part_no: "MTR-CBL-IG5A"`, 실제는 끝에 A가 없는 `MTR-CBL-IG5`)를 시도했고
`search_inventory`·`get_supplier_quotes`가 둘 다 0건으로 돌아왔다. **이건 버그가
아니라 시스템이 올바르게 동작한 것**(가짜 부품을 지어내지 않고 정직하게 "없음"으로
답함) — 하지만 데모에서 이걸 겪으면 "안 되네?"로 오해하기 쉽다. 실제 OCT+iG5A 관련
부품은 DB에 이렇게 등록돼 있다:

```
error_codes.related_parts (iG5A, OCT) = ["MTR-CBL-IG5"]
parts.name = "모터 출력 케이블"
inventory: 재고 2 / 안전재고 1 / 자재창고 A-08
```

대사에서 "배선 점검해보니 **케이블이 마모**되어 있었어요"처럼 자연스럽게 이 부품을
가리키는 표현을 쓰면 된다 — "모터 출력 케이블"이라는 이름을 그대로 말할 필요는 없고,
핵심은 **실존하는 부품을 가리키는 설명**이어야 한다는 것.

## ④ Docker로 백엔드를 띄울 땐 `host.docker.internal` 필수

MaintQ 백엔드를 `docker compose up`으로 띄우면, 컨테이너 안에서의 `localhost`는
**컨테이너 자기 자신**을 가리킨다. `.env`의 `MAINTQ_A2A_FINALLQ_BASE_URL=http://localhost:9101`
을 그대로 컨테이너에 넘기면 재무 승인 시점에 A2A 출금요청이 **"Cannot connect to A2A
adapter at http://localhost:9101"** 로 무조건 실패한다(FinAllQ 어댑터가 호스트에
bare 프로세스로 떠 있어서). InsuQ 쪽(9102)도 같은 문제(InsuQ 어댑터는 도커 컨테이너지만
그 컨테이너와 MaintQ 컨테이너는 다른 네트워크라 역시 `localhost`로는 안 닿는다).

**해결**: `docker-compose.override.yml`(신규, gitignore 처리해 둠 — 개인 로컬 포트
설정이라 커밋 대상 아님)에서 다음을 덮어쓴다:

```yaml
services:
  backend:
    ports: !override
      - "8897:8000"   # 8003은 FinAllQ mcp-hub와 충돌해서 격리 포트 사용
    environment:
      MAINTQ_TOOLS_PROFILE: full   # 확장 도구 20종 — 이거 없으면 assess-loan 자체가 안 뜬다
      MAINTQ_CORS_ORIGINS: http://localhost:3003,http://127.0.0.1:3003
      MAINTQ_A2A_FINALLQ_BASE_URL: http://host.docker.internal:9101
      MAINTQ_A2A_INSUQ_BASE_URL: http://host.docker.internal:9102
```

`frontend/.env.local`의 `NEXT_PUBLIC_API_BASE`도 `http://localhost:8897`로 맞춰야
한다(gitignore 대상, 개인 파일). **이 두 파일은 이 컴퓨터에만 있다** — 다른 컴퓨터·다른
사람 환경에서 재현하려면 이 노트대로 다시 만들어야 한다.

## ⑥ 장비 선택 드롭다운 — 마우스 클릭이 안 먹을 수 있다

`<option>`을 나열하는 DOM 특성" 관련 오진 사례가 있었는데, 이번 건 그것과는 다른
증상(진짜로 값이 안 바뀜)이었다.

## ⑨ (부록) 세 번째 A2A 시나리오 — lookup-clause(약관 조회) 타임아웃 3중 구조

시나리오 1·2 외에 **MaintQ→InsuQ 단일 홉**(`search_insurance_clause` MCP 도구, A2A 스킬명
`lookup-clause`)도 실제로 동작한다 — 단, 처음엔 항상 타임아웃났다. 원인을 파고드니
**타임아웃이 3중으로 걸려 있었다**:

1. MCP 도구 자체(`mcp_server/tools/search_insurance_clause.py`) — 원래 12초
2. 백엔드 A2A 클라이언트 호출(`backend/routers/a2a.py`의 `call_skill(...)`) — 원래 기본값 10초
   (`backend/a2a/client.py::call_skill`의 파라미터 기본값)
3. **에이전트 루프 전역 상한** `backend/agent/mcp_client.py::TOOL_TIMEOUT_SEC = 10.0` —
   `09_RUNTIME.md §2`에 문서화된 설계 상수로, **모든 MCP 도구 호출에 예외 없이 적용**되던
   것(`loop.py`가 "재정의하지 않는다"고 주석까지 달아둠).

InsuQ의 실제 RAG 응답 시간은 curl 직결 실측 **11.3초** — ③번 전역 10초 상한 때문에 ①②를
아무리 늘려도 항상 그 전에 끊겼다. **사용자 확인 후** ③에 `search_insurance_clause` 하나만
예외를 두는 방식으로 해결(`_TOOL_TIMEOUT_OVERRIDES` 딕셔너리 신설, 25초) — 다른 19종
도구의 기본 10초 상한은 그대로 유지된다. 세 곳 다 수정 완료(커밋 안 됨):

- `mcp_server/tools/search_insurance_clause.py` (30초)
- `backend/routers/a2a.py` (lookup-clause 호출에 `timeout=25.0` 명시)
- `backend/agent/loop.py` (`_TOOL_TIMEOUT_OVERRIDES` 신설)

수정 후 실측: 9.7초 만에 InsuQ 보통약관·특별약관 조항 8건 인용까지 포함한 완전한 답변
성공(judgement: "판단 유보" — 손해 대상이 인버터 자체인지 다른 목적물인지 InsuQ도 추가
확인이 필요하다고 정직하게 답함).

**다음 세션 할 일**: 이 3개 파일 커밋. `TOOL_TIMEOUT_SEC`를 손대지 않고 예외 목록 방식을
택한 이유는 09_RUNTIME.md가 문서화한 전역 상한을 건드리면 다른 회귀·문서 정합성에 영향이
갈 수 있어서다 — 커밋 메시지에 이 판단 근거를 남길 것.

## ⑩ (2026-08-25 추가) FinAllQ 승인 후 "추가 인증 필요"로 멈추는 게 정상 — FDS 분기

실제 촬영(2026-08-25 새벽) 중 `/transfers/approvals`에서 승인을 눌렀는데 `completed`가 아니라
**추가 인증 필요(TOTP)** 상태로 바뀌었다. 버그 아님 — FinAllQ `ai/services/fds.py::score_transaction`이
`a2a-service` 계정을 고위험으로 판정한 것. 원인은 금액이 아니라 **"첫 거래 + 심야 시간대" 조합**:

- `a2a-service`는 거래 이력이 없어 Redis 프로필 `avg_amount=0` → 비율 계산이 사실상 요청 금액
  그 자체가 되어 `EXCESSIVE_AMOUNT_RATIO` 사유코드 발생
- 자정 넘은 시각(KST)이면 `NIGHT_TRANSACTION` 사유코드도 같이 뜬다
- 사유코드가 2개 이상이면 `risk_score`와 무관하게 `REQUIRE_2FA` — **낮 시간대에 찍으면 이 분기
  자체가 아예 안 뜰 수 있다.** 시간대를 바꿀 수 없다면 이 분기가 뜬다는 걸 미리 각오할 것.

TOTP는 요청자(a2a-service)가 아니라 **결재자(demo-manager) 본인**이 인증하는 구조이고
`demo-manager`는 2026-08-21에 이미 TOTP 등록이 돼 있다 — 그날 스캔해둔 인증 앱이 있으면
그걸로 뚫을 수 있다. **이번 촬영에서는 그 앱을 못 찾아서 재등록 대신 "결재 대기 / 추가 인증
필요" 상태에서 멈추는 쪽으로 결정했다** — 오히려 "A2A라고 무조건 자동승인 되는 게 아니다,
고위험이면 FinAllQ가 사람 2FA를 요구한다"를 보여주는 자연스러운 지점이라 나쁘지 않은 결말이다.
대사 예: *"이 요청은 처음 나가는 거래인 데다 시간대도 이례적이라, FinAllQ가 자동승인 대신
사람의 2차 인증을 요구합니다 — A2A가 결제까지 전부 대신할 수는 없다는 설계입니다."*

다음에 완주(TOTP 통과 → `completed`)까지 보여주고 싶으면 촬영 전 `demo-manager` 계정의
