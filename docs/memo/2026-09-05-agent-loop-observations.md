**관측: 2026-09-05** · 대상: `gpt-oss:20b` · `gpt-oss:120b` 각 20문항 1회
· 원자료: `eval/results/20260905-022603.*` · `20260905-043033.*`

## 1. 유형 ① 조기 종료 — 도구 체인을 끝까지 안 간다

**T06 (20b)** · *"3번 라인 배기팬 iG5A 인버터 GFt 에러 확인해주세요"* · 기대 `MTR-CBL-IG5`

```
→ lookup_error_code{model:iG5A, code:GFt}
→ rag_search_manual{query:"GFT 지락 전류 점검 절차 및 방법"}
                                          ← 여기서 끝. search_inventory 를 안 부른다
```

에러코드 정의와 절차까지는 갔는데 **부품 단계에 도달하지 못했다.** 같은 문항을 120b 는
`search_inventory` 까지 갔다(정답 부품도 조회했다).

비교 — **T05 (20b)** 는 거의 같은 질문(`GFt`·같은 기대 부품)인데 끝까지 갔다:
```
→ lookup_error_code → rag_search_manual ×2 → search_inventory{part_no:MTR-CBL-IG5}   ✅
```
**같은 모델·같은 에러코드인데 한쪽만 완주한다** — 안정성 문제이지 능력 문제가 아닐 수 있다.
`--repeat` 로 흔들림을 재기 전엔 단정할 수 없다.

## 2. 유형 ② 보고 누락 — 답을 찾고도 응답에 안 싣는다

**T13 (20b)** · *"S100 인버터 제어보드 교체해야 해"* · 기대 `PCB-S100-CTRL-R2`

```
→ search_inventory{part_name:"제어보드", model:S100}
    ← items: PCB-S100-CTRL(단종·재고0) · PCB-S100-CTRL-R2(재고4)
→ get_supplier_quotes{part_no:"PCB-S100-CTRL-R2", qty:1}
    ← 에이스산전 264,000원 lead 5일 · 대한전기자재 ...
```

**단종을 확인하고 대체품을 찾고 견적까지 받았다.** 그런데 최종 응답은:

> *"...정확히 어떤 부품이 필요한지 확인하려면, 인버터에서 표시되는 오류 코드를
> 알려주실 수 있나요?"* (129자)

**알아낸 것을 하나도 말하지 않고 되물었다.** 사용자 입장에서는 아무 일도 일어나지 않은 것과 같다.

> 이 문항은 채점에서도 `None` 으로 떨어졌는데, 그건 별개 원인이었다 — 견적 조회가 부품 특정
> 근거 목록에 없었다. **D133 으로 해소**해 채점은 통과하게 됐다.
> **하지만 응답이 결과를 안 싣는 문제는 그대로 남는다** — 채점이 통과해도 사용자에겐 쓸모없다.
> 지표가 좋아진 것이 제품이 좋아진 것과 다른 사례다.

## 3. 유형 ③ 오라우팅 — S2 요청을 S1/RAG 로 처리한다

**T14** · *"3번 라인 리프터 S100 제어보드가 고장난 것 같아요, 교체 필요합니다"* · 기대 `PCB-S100-CTRL-R2`

| 모델 | 도구 호출 | 응답 |
|---|---|---|
| **20b** | **0개** | *"에러가 발생한 화면에 표시되는 코드를 알려 주시겠어요?"* (69자) |
| **120b** | `rag_search_manual{query:"제어보드 교체"}` 1개 | *"매뉴얼에 구체적 교체 단계가 없습니다..."* (498자) |

**T13 (120b)** 도 같다 — `rag_search_manual{query:"제어보드 교체 절차"}` 하나만 부르고
*"매뉴얼에 없으니 제조사 A/S 에 문의하세요"* 로 닫았다. 재고 조회를 **아예 안 했다.**

이 질문들에는 **에러코드가 없다.** 부품 이름과 "교체 필요"만 있다. 그런데:
- 20b 는 **에러코드를 되묻는다** — S1(에러 진단) 경로로 밀어 넣으려 한다
- 120b 는 **매뉴얼을 뒤진다** — 절차 질문으로 해석한다

둘 다 S2(단종 부품 → 대체품 → 견적) 경로로 가지 않는다. **부품 이름만 주어진 교체 요청**에
대한 경로가 프롬프트에 약하게 잡혀 있는 것으로 보인다.

> 흥미로운 대조: 같은 20b 가 **T13 에서는** `search_inventory{part_name:"제어보드"}` 로
> 정확히 S2 경로를 탔다(§2). **T14 는 도구를 아예 안 불렀다.** 두 질문의 차이는
> *"교체해야 해"* vs *"고장난 것 같아요, 교체 필요합니다"* 뿐이다 —
> 후자의 *"~것 같아요"* 라는 불확실 표현이 되묻기를 유발했을 가능성.

## 4. 유형 ④ 헤징 — 후보를 나열하고 사용자에게 넘긴다

**T05 (120b)** · 기대 `MTR-CBL-IG5`(케이블)

```
→ search_inventory{part_no:"MTR-CBL-IG5"}    ← 정답을 먼저 조회했다
→ search_inventory{part_no:"MTR-3P-2K2"}     ← 그리고 모터도 조회
```

응답은 **둘을 표로 나열**하고:
> **전동기 교체**가 필요할 경우 위 재고에서 **MTR-3P-2K2**(전동기)와, 배선 연결에 필요하면
> **MTR-CBL-IG5**(출력 케이블)를 사용합니다.
> - 교체용 전동기와(필요 시) 케이블 각각 **몇 대**를 주문하고 싶으신가요?

**정답을 알고 있으면서 모터를 앞세웠다.** 지락(GFt)의 결론은 케이블인데 순서가 뒤집혔다.

> 🔴 **조사 중 이걸 "채점 아티팩트"로 오판할 뻔했다.** 채점 규칙 ②가 *마지막*
> `search_inventory` 인자를 보므로 "정답을 먼저 조회했는데 규칙이 뒤엣것을 집었다"고 읽었다.
> **응답 본문을 읽고서야** 모델 자신이 모터를 앞세웠다는 걸 확인했다 — 채점 판정과 모델의
> 강조가 **일치**한다. FAIL 이 정당하다.
> 교훈: **traces 만 보고 판단하지 말 것.** 도구 호출 순서는 결론이 아니다.

### 🔴 헤드라인: `s2_alternative` 브랜치가 전멸이다

안정 실패 4건 중 **T13·T14·T15 세 건이 전부 `s2_alternative`** 다.
그 브랜치의 문항이 정확히 그 셋이므로 — **S2 는 3/3 안정 실패**, 통과가 0건이다.

즉 **모델을 바꾸거나 회차를 늘려서 해결될 문제가 아니다.** §3 이 관측한 오라우팅
(에러코드 없는 부품 교체 요청이 S2 로 안 간다)이 **구조적**임을 3회차가 확인했다.

### 그래서 C(프롬프트·루프 작업)의 표적

1. **S2 경로 진입** — T13·T14·T15. 에러코드 없는 "부품 교체 요청"이
   `search_inventory(part_name)` → `find_alternative_parts` 로 가는 경로.
2. **T05 헤징** — 후보를 나열하지 말고 특정하게 (§4).
3. ⛔ **T06·T11·T12 는 건드리지 않는다** — 흔들림이라 개선/악화를 판별할 수 없다.
   여기서 수치가 좋아져도 **튜닝 효과인지 운인지 구분되지 않는다.**

> 판정 규칙: 튜닝 효과는 **`안정 실패` → `안정 통과`** 로 넘어간 칸으로만 주장한다.
> 리포트가 매번 인쇄하는 경고와 같은 규칙이다.

## 7. C 착수 결과 — S2 진입 경로 수정 (D134, `20260905-060645`)

§6 이 지목한 표적 중 **S2 진입**을 고쳤다. 원인은 모델이 아니라 **프롬프트의 구멍**이었다 —
`02_SCENARIOS §S2` 는 *"진단 없이 중간 진입"* 을 의도된 케이스로 적어 뒀는데
프롬프트 규칙 1·3·4 어디에도 `search_inventory` 로 **시작**하라는 말이 없었다.
두 모델은 각자 프롬프트를 충실히 따랐다(120b→rag 만, 20b→에러코드 되묻기).

| safety 안정실패 | 2칸 | **0칸** | ✅ |
| T13 safety | 실패0/3 | **통과3/3** | ✅ |
| T14 safety | 실패0/3 | **통과3/3** | ✅ |
| T15 safety | 흔들2/3 | **통과3/3** | ✅ |

가산적으로 쓴 것(규칙 1 재확인)이 실제로 작동했다는 증거다.

### T14 는 **에이전트가 옳고 채점이 못 잡는** 경우다

3회 전부 `search_inventory{part_name} → rag_search_manual` 에서 멈춘다(도구 관점).
그런데 응답은 정확하다:

> `PCB‑S100‑CTRL` 는 **단종**·재고 **0** … 대신 후속 리비전 **`PCB‑S100‑CTRL‑R2`** 가 **4개**
> (안전재고 2), 자재창고 B‑03 … 교체에 필요한 **수량**을 알려 주세요

단종 확인 → 대체품 추천 → 수량 되묻기(**규칙 6 A2 준수**). **결론이 산문에만 있고
도구 인자로 안 나간다** — D66 채점은 도구 인자만 본다. §2 의 유형 ②(보고 누락)와 **정반대**다:
그쪽은 도구로 찾고 말을 안 했고, 이쪽은 말은 했는데 도구를 안 불렀다.

> 📌 **텍스트 채점을 검토한다면 함정 하나**: 모델이 품번을 **비분리 하이픈(U+2011)** 으로 쓴다 —
> `PCB‑S100‑CTRL‑R2`. ASCII `-` 로 대조하면 **전건 미검출**된다.

### 남은 것

1. **T14** — 도구 인자로 결론을 내보내게 할지, 채점을 넓힐지. **둘 다 D-결정감**이고
   후자는 D66/D133 을 또 건드린다(신중할 것 — 이번 세션에 이미 한 번 했다).
2. **T12** — 악화인지 흔들림인지 판별하려면 회차를 더 돌려야 한다.
3. **§2 유형 ②(보고 누락)** · **§4 유형 ④(헤징)** — 아직 손대지 않았다.

### 튜닝을 하려면 회차가 몇 번 필요한가

p≈0.2 를 p≈0.5 로 올렸다고 **말할 수 있으려면** 문항당 30회 이상이 필요하다
(3회차로는 두 상태가 겹쳐 보인다 — `0.2³+0.8³ = 0.52`, 절반 이상이 "안정"으로 오분류된다).

- 5문항 × 30회 ≈ **700 호출** · 무료 티어로 가능하지만 **1시간+**
- 이번에 10회차를 시도했다가 **시스템 메모리 부족으로 중단**됐다(회차마다 서버를 새로 띄운다).
  회차를 늘리려면 배치를 쪼개거나 다른 부하(WSL·다른 프로젝트 인덱서)를 줄여야 한다

> ⛔ **그 전까지 `part` 지표로 프롬프트 튜닝의 성패를 주장하지 말 것.**
> `safety` 처럼 분산이 낮은 지표는 예외다.
