**측정: 2026-09-06** · 대상 `gpt-oss:20b` · 5문항 × **20회차**(10회차 배치 2개 병합)
· 원자료 `eval/results/noise30/20260906-002713.*` · `20260906-010049.*`

> 직전 세션(`sessions/2026-09-05-eval.md`)의 「다음 세션」 1·3번이 요구하던 측정 예산이다.
> 3회차로는 *"안정 실패"* 를 주장할 수 없다는 것이 D134 사후 정정에서 이미 드러났고,
> 이 문서는 그것을 20회차로 확정한다.

## 0. 한 줄

**`gpt-oss:20b` 의 `part` 칸이 20회차에서 전부 흔들렸다 — 안정통과 0 · 안정실패 0 · 흔들림 5.**
`part` 를 근거로 튜닝 성패를 주장하려면 문항당 20회차로도 **모자란다.**

그리고 §5 — **`part` 합계는 45.6%(120b) vs 51.0%(20b) 로 갈리지 않는데,
분기로 묶으면 `s1_pipeline` 에서 8.3% vs 47.5% 로 확실히 갈린다.**
합계가 상쇄해 숨긴다 — 모델 선택의 근거는 합계가 아니라 분기별 수치다.

## 5. 모델 비교 — 합계는 같고 문항별로는 정반대다

### 120b 표본을 어떻게 만들었나 (추가 LLM 호출은 마지막 8회차분뿐)

120b 배치는 **다섯 개 중 다섯 개가 다 죽었다**(§6). 그런데 **죽기 전에 완주한 회차의
traces 는 남아 있다.** `score.py` 의 판정은 전부 `score_session(events, expected)` —
`response_text` 를 쓰지 않으므로 **저장된 traces 만으로 완전 재채점된다.**

| 출처 | 회차 |
|---|---|
| `probe/20260906-001619` (원인 조사용, 리포트 있음) | 4 |
| `000653` r1·r2 + `000955` r1~r3 + `001526` r1 (경합 구간에 죽은 배치) | 6 |
| `055349` r1~r7 + `060302` r1 (단독 실행인데도 죽은 배치) | 8 |
| **합계** | **18** |

> 🔴 **순서 규칙을 지켰다** (memo/eval-harness-debug §3 ②): 되살리기 **전에**
> probe 리포트의 문항별 판정 **60칸을 재채점으로 대조해 불일치 0** 을 확인했다.
> 재현 못 하는 하네스의 결과는 무의미하다. 폴백 혼입도 0건(모델이 섞이지 않았다).

### `part` — 합계가 숨긴 것

| 문항 | 분기 | `gpt-oss:120b` (n=18) | `gpt-oss:20b` (n=20) | 구간 |
|---|---|---|---|---|
| T05 | s1_pipeline | **0/18 0%** [0%, 18%] | 10/20 50% [30%, 70%] | **안 겹침** |
| T06 | s1_pipeline | 3/18 17% [6%, 39%] | 9/20 45% [26%, 66%] | 겹침 |
| T13 | s2_alternative | 9/18 50% [29%, 71%] | 3/20 15% [5%, 36%] | 겹침 |
| T14 | s2_alternative | 11/18 61% [39%, 80%] | 10/20 50% [30%, 70%] | 겹침 |
| T15 | s2_alternative | 18/18 100% [82%, 100%] | 19/20 95% [76%, 99%] | 겹침 |
| **합계** | | **41/90 = 45.6%** | **51/100 = 51.0%** | |

**문항 단위로는 T05 하나만 갈린다.** n=18·20 으로도 나머지 넷은 구간이 겹친다.

### 분기로 묶으면 갈린다

| 분기 | 120b | 20b | 구간 |
|---|---|---|---|
| `s1_pipeline` (T05·T06) | **3/36 = 8.3%** [3%, 22%] | **19/40 = 47.5%** [33%, 63%] | **안 겹침** |
| `s2_alternative` (T13·T14·T15) | 38/54 = 70.4% [57%, 81%] | 32/60 = 53.3% [41%, 65%] | 겹침 |

- **`s1_pipeline` 은 20b 가 확실히 이긴다** — 8.3% vs 47.5%, 구간이 멀찍이 떨어진다.
- **`s2_alternative` 는 120b 쪽으로 기울지만 확정은 아니다** (70.4% vs 53.3%, 겹침).
- **합계(45.6% vs 51.0%)는 이 둘을 상쇄해 "차이 없음"처럼 보이게 만든다.**

> 직전 세션의 `20b 80%` vs `120b 60%` 는 **"노이즈였다"로 닫으면 안 된다.**
> 20문항의 s1/s2 **구성비**가 만든 값일 수 있다 — 모델 순위를 매기려면 **분기별로 따로** 재야 한다.

### 🔴 정정 — n=10 에서 내가 한 주장 셋 중 둘이 무너졌다

이 절은 처음에 **n=10**(probe 4 + 복구 6)으로 썼고, 거기서 세 가지를 "구간이 겹치지
않는다"고 주장했다. n=18 로 늘리자:

| n=10 에서의 주장 | n=18 실측 | 판정 |
|---|---|---|
| T05 `0/10` — 20b 와 안 겹침 | `0/18` [0%,18%] | ✅ **유지** |
| T06 `0/10` — 20b 와 안 겹침 | `3/18` 17% [6%,39%] → **겹침** | ❌ **철회** |
| T13 `7/10 70%` — 20b 와 안 겹침 | `9/18` 50% [29%,71%] → **겹침** | ❌ **철회** |

**같은 세션 안에서 세 번째로 반복된 함정이다.** 이 문서 §4·§5 가 *"회차가 적으면 극단값이
나온다"* 고 경고해 놓고, 바로 그 다음 문단에서 n=10 극단값으로 결론을 냈다.
`0/10`·`7/10` 은 `0/4` 보다 나을 뿐 **여전히 중앙으로 회귀한다.**
문항 단위 주장은 n≈20 으로도 부족하고, **묶어서(분기 단위) 봐야 한다.**

### `citation`·`safety` — 여기선 120b 가 낫다 (확정)

| | 120b (n=90) | 20b (n=100) | 구간 |
|---|---|---|---|
| citation | **100%** (90/90) | 86% | 안 겹침 |
| safety | **94.4%** (85/90) | 77% | 안 겹침 |

표본이 커서 이 둘은 문항 단위 요동에 흔들리지 않는다. **인용·안전 경고는 120b 가 낫다.**

### T15 (§4 보강)

**두 모델에서 함께 높다** — 120b `18/18`, 20b `19/20`. D134 효과가 모델 특성이 아니다.

## 6. `[WinError 10014]` — 코드 결함이 아니라 자원 경합

배치 6개 중 4개가 회차 도중 죽었다. 전부 같은 예외다:

```
File "eval/run_eval.py", line 1533, in _run_round
    if not asyncio.run(_wait_ready(base_url)):
  ... socket.socketpair() → lsock.listen()
OSError: [WinError 10014] 잘못된 포인터 주소
```

처음엔 **3회차에서 결정적으로 죽는 구조적 결함**으로 보였다(배치 1·2가 둘 다 정확히
3회차에서 죽었다). **틀린 해석이었다.**

### 계측으로 배제한 것

10초 간격으로 회차 내내 잰 값(`freeMB` · 서버 프로세스 수 · 러너 RSS · 핸들 수):

| 검사 | 실측 | 판정 |
|---|---|---|
| 서버 프로세스 누적 | 회차마다 `4 → 8 → 4` **기준선 복귀** | 누수 없음 |
| 핸들 누적 | `~920 ↔ ~1840` **기준선 복귀** | 누수 없음 |
| 러너 RSS | 4회차에 걸쳐 79 → 168MB | 폭주 없음 |
| 머신 여유 메모리 | **1,606 ~ 3,080MB / 32,328MB** | 압박 |

`_shutdown_server` 의 `taskkill /T /F` 는 정상 동작한다. 조사 중 발견한 고아 uvicorn
트리는 **내가 큐를 회차 도중 강제 종료해서 생긴 것**이었지 정상 경로의 누수가 아니었다.

### 경합은 크게 악화시키지만, 유일한 원인은 아니다

| 시각 | 동시 실행 | 결과 |
|---|---|---|
| 09:06 ~ 09:27 | 큐 + 원인 조사 실행 **2개** | 배치 4개 실패 — 살아남은 회차 **1·2·2·3** |
| 09:27 ~ 10:28 | 큐 **단독** (20b) | 배치 2개 **10/10 완주** ✅ |
| 14:53 ~ 15:04 | **단독** (120b) | b1 **7회차 뒤 실패**, b2 **2회차에서 실패** ❌ |

> 🔴 **처음엔 "경합만 없으면 멀쩡히 돈다"고 결론지었다. 마지막 줄이 그걸 반증했다.**
> 단독 실행으로 살아남는 회차가 1~3 → 7 로 크게 늘긴 했지만 **완주를 보장하지는 않는다.**
> 게다가 b2 는 `WinError 10014` 가 아니라 **`MCP 가 기동하지 않았습니다`(`mcp: False`)**
> 라는 다른 모드로 죽었다 — 같은 뿌리(회차 시작 시 자원 할당)에서 갈라진 두 증상이다.

실패는 **항상 회차 시작 지점**이다(서버·MCP 스폰 + 새 이벤트 루프 생성). 문항 실행 중에
죽은 적은 한 번도 없다. 이 머신의 여유 메모리를 먹는 것은 `vmmemWSL` **7,850MB**
(다른 프로젝트 컨테이너 12개)이고, 평가가 겹치면 거기에 uvicorn(~130MB)+MCP(~88MB)가 더 얹힌다.

### 그래서 규칙

- **평가 실행 중에 다른 평가를 띄우지 않는다.** 효과가 가장 큰 한 가지다.
- **배치가 죽어도 잃는 것은 "아직 안 돈 회차"뿐이다** — 완주한 회차는 traces 재채점으로
  전부 회수된다(§5·§7). 이번 120b 표본 18회차 중 **14회차가 죽은 배치에서 나왔다.**
  그래서 `--repeat` 를 크게 잡아도 손실이 크지 않다.
- 리포트(`.json`)는 배치가 죽으면 안 생기므로, **회차별 `.rN.traces.jsonl` 이 진짜 원본**이다.
- CLAUDE.md 가 스파이크에 대해 적어 둔 *"단독 재실행하면 통과한다"* 와 **같은 부류**다.

## 7. 재는 방법

```bash
# 5문항 부분집합 (T05·T06·T13·T14·T15) 을 testset 으로 만들어
uv run python eval/run_eval.py --testset <부분집합>.json --repeat 10 --yes \
    --out-dir eval/results/noise30
# 모델은 env 로 고른다 (.env 의 MAINTQ_LLM_MODEL 을 OS env 가 이긴다)
MAINTQ_LLM_MODEL=gpt-oss:20b  uv run python eval/run_eval.py ...
```

**배치가 죽어도 완주한 회차는 버리지 않는다.** 리포트(`.json`)는 안 남아도
회차별 `.rN.traces.jsonl` 은 남아 있고, `score.score_session(events, expected)` 가
`events` 만으로 `part`·`citation`·`safety` 를 전부 판정하므로 **LLM 호출 0회로 재채점**된다
(`session_id` 는 `EVAL-<문항id>`). 이번에 그렇게 120b 6회차를 되살렸다 — 되살리기 **전에**
살아 있는 리포트로 재현성부터 단언할 것(§5).

배치를 이어붙여 흔들림을 다시 낼 때는 **판정 정의를 재구현하지 말 것** —
`eval/run_eval.py` 의 `item_outcomes()` · `flip_analysis()` 정본을 그대로 부른다.
재구현하면 리포트와 표가 조용히 갈라진다. (병합 스크립트는 일회용이라 레포에 두지 않았다.
`items[]` 레코드에 `events` 가 없으므로 `excluded_stream=0` · `excluded_failed=0` ·
캐시 히트 0 을 리포트에서 확인한 뒤 `events=[]` · `llm_stream_failed=False` 로 채운다.)
