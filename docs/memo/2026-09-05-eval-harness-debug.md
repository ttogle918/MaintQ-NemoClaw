## 1. 조용히 거짓을 내던 경로 셋

### ㉠ traces 0행 — 평가가 아무도 안 쓴 DB 를 읽었다 (D130)

2026-08-29 리포트가 자기 증상을 이미 적어 두고 있었다:

```
- 잘린 턴: 0건 / LLM 호출 56회 (종료 사유: STOP×20, TOOL_CALLS×36)
- traces 덤프: ...traces.jsonl — 0행
```

**도구를 36번 부르고 trace 0행.** 원인은 하네스가 SQLite 사본을 자식 서버에 `MAINTQ_DB` 로
넘긴 것 — **Postgres 백엔드는 그 변수를 읽지 않는다.** 자식은 상속받은 `DATABASE_URL` 로
공유 `public` 에 쓰고, 스크립트는 아무도 안 쓴 사본을 읽었다.

> 이 구멍은 **평가를 무의미하게 만드는 동시에 실 DB 를 오염**시켰다.
> 2026-09-05 실행에서 `traces 176행`·`182행` 이 나오며 D130 수정이 먹혔음이 **처음 확인됐다.**

### ㉡ 빈 응답이 오답으로 채점됐다 (D132)

모델 EOL + 폴백 크레딧 소진으로 20문항이 전부 빈 응답이 됐는데, 예외가 러너까지 올라온
**2건만** 분모에서 빠지고 **나머지 18건은 실질 오답으로 채점**됐다.

```
part: 53.3% → 0.0% (-53.3pt)      ← 가짜 회귀
```

스트림 실패는 **HTTP 200 에 빈 본문**으로 온다. 러너는 *"응답을 받은 것"* 과 구분하지 못한다 —
서버가 남긴 `[LLM_END] reason=STREAM_ERROR` 만이 그 구분을 갖는다.

판정 규칙은 `stream_failed_sessions()` **한 곳**이 소유하고 `aggregate()` 와 `item_outcomes()` 가
같이 읽는다. 세션의 **전 호출**이 실패했을 때만 뺀다(`all`) — `any` 로 느슨하게 하면 부분 실패까지
빠져 **지표가 부풀려진다.** 제외는 정직해지는 방향으로만 쓴다.

> **레코드가 0건이면 아무것도 빼지 않는다.** `[LLM_END]` 파싱이 깨졌을 때 "전부 실패"로 접으면
> 모든 문항이 조용히 분모에서 빠져 **지표가 통째로 사라진다.** *계측 불능*과 *실패*는 다르다.

### ㉢ 폴백 원인이 타입 이름만 남았다 (D131)

```
LLM 제공자 폴백: nvidia → openai (원인 APIStatusError)
```

모델 EOL(410) · 키 만료(401) · 권한(403) · 쿼터 소진(429)이 **전부 같은 타입으로 뭉개진다.**
넷은 조치가 전부 다르다. 원인을 알아내려고 엔드포인트를 직접 curl 로 찔러야 했다.

**본문은 여전히 안 남긴다** — `test_llm_fallback.py` 가 `"status 401" not in caplog.text` 로
명시적으로 금지하고 있고 D123 이 가짜 키 실증으로 그 성질을 확인 사항에 적어 뒀다.
상태코드는 정수라 누출 위험이 없고 넷을 가르는 데 충분하다.

## 2. 오진 1건 — 제일 값진 기록

조사 중 *"채점 규칙이 `parts` 라는 없는 키를 읽어 죽어 있다"* 고 **확정 버그로 단정하고
수정까지 했다가 되돌렸다.**

원인은 단순하다. `traces` 의 `tool_result` 레코드에 **필드가 둘**인데 엉뚱한 쪽을 셌다:

```
data         = {"tool":..., "status":"ok", "summary":..., "pages":[], "parts":["FAN-IG5-01"]}
                                                                       ↑ score.py 가 읽는 것
tool_payload = {"items":[{"part_no":"FAN-IG5-01", "qty":1, ...}], "status":"ok"}
                 ↑ MCP 원본 (D76-2 가 추가한 감사용). 내가 센 쪽
```

`score.py::_tool_results()` 는 `ev.get("data")` 를 돌려준다. 거기 `parts` 가
**30/30 전건 존재**하고 `list[str]` 이다. 규칙은 **정상 동작 중이었다.**

**잡아낸 것은 재채점 diff 였다** — "수정본"이 `0/15` 라는 말도 안 되는 값을 내서 그제서야
하네스를 의심했다. 수치가 그럴듯했다면 그대로 커밋했을 것이고, **부품 지표가 통째로 망가진 채**
아무도 몰랐을 것이다.

> **규칙: 채점기를 고치기 전에 저장된 traces 로 재채점해 알려진 실측(리포트 지표)을
> 재현하는지 먼저 단언한다.** 재현 못 하는 하네스의 diff 는 무의미하다.

교훈 둘:
- *"전수 조사했다"* 는 말은 **무엇을 세었는지**가 맞아야 성립한다. 30건을 다 세도 필드를
  잘못 고르면 0건이 나온다.
- **자기 도구를 먼저 검증한다.** 아래 §3 의 스크립트는 그래서 맨 앞에 자기 검증을 둔다.

## 3. 오프라인 재채점 (LLM 호출 0회)

저장된 `.traces.jsonl` 로 채점 규칙 변경의 효과를 **돈 안 쓰고** 잰다.

```python
# ① 이벤트 재구성 — 페이로드는 반드시 `data` 아래다 (§2 의 함정)
def events_by_session(stamp):
    out = defaultdict(list)
    for ln in open(f"eval/results/{stamp}.traces.jsonl", encoding="utf-8"):
        r = json.loads(ln)
        out[r["session_id"]].append(
            {"event": r["event"], "tool": r.get("tool"), "data": r.get("data")}
        )
    return out

# ② 변형을 재기 **전에** 하네스 자신을 검증한다
#    현행 score.py 로 리포트의 실측(예: 20b 12/15 · 120b 9/15)을 재현하지 못하면 즉시 중단.
#    재현 못 하는 하네스의 diff 는 무의미하다.

# ③ 그 다음에야 변형을 잰다
```

`session_id` 는 `EVAL-<문항id>` 다(`run_eval.session_id_for()` 한 곳이 만든다).

## 5. `--repeat 3` 은 안정성 판정에 부족하다 (2026-09-05, A/B 대조로 발견)

리포트는 회차 간 판정이 갈리는 칸을 `흔들림` 으로, 안 갈리는 칸을 `안정 통과`/`안정 실패` 로
분류한다. 그리고 *"튜닝 효과는 `안정 실패` → `안정 통과` 로 넘어간 칸으로만 주장한다"* 가
이 레포의 판정 규칙이다. **그 규칙 자체는 옳다. 그런데 `--repeat 3` 으로는 그 분류가 안 선다.**

### 실측

같은 코드(D134 상태)·같은 문항 T14 `part` 가 **실행에 따라 반대로 나왔다**:

| 실행 | 구성 | T14 part |
|---|---|---|
| `20260905-060645` | 20문항 × 3회차 | **실패 0/3** |
| `20260905-091641` | 3문항 × 3회차 | **통과 3/3** |

**`안정 실패` 와 `안정 통과` 가 같은 코드에서 둘 다 나온다.**

### 왜 이런 일이 생기나

3회차는 **회차 간(within-run) 흔들림**만 잰다. 그런데 흔들림은 **실행 간(between-run)** 에도
있다. 문항의 통과 확률이 대략 p 라면, p 가 0.5 근처여도 3연속 같은 결과가 나올 확률은
`p³ + (1-p)³ = 0.25` 다 — **네 번에 한 번은 "안정"으로 오분류**된다. p 가 0.7·0.3 쪽이면 더 잦다.

### 그래서

- **3회차 "안정 실패"를 튜닝 표적으로 확정하지 말 것.** 표적이 아닐 수 있다.
- **3회차 "안정 실패 → 안정 통과" 를 성과로 주장하지 말 것.** 둘 다 오분류일 수 있다.
- ✅ **회차 분산이 0 인 지표는 신뢰도가 다르다.** 예: `safety` 는 서로 다른 두 실행에서
  각각 83.3%·94.4% 로 **3회 내내 동일**했다 — 그런 지표의 변화는 노이즈로 보기 어렵다.
  `part` 는 같은 실행 안에서도 20pt(60.0/53.3/73.3) 흔들린다. **지표마다 노이즈가 다르다.**
- ✅ **표적 문항만 골라 고회차로 재라.** 20문항 × 10회 = ~940 호출이지만
  **5문항 × 10회 = ~230 호출**이면 15분이다. 튜닝 전에 **노이즈 바닥을 먼저 확정**한다.
- ✅ **프롬프트 변경은 A/B 대조로 판정하라** — 같은 testset·같은 회차로 변경 전/후를
  **각각** 돌린다. "이전 실행 대비"는 구성이 다르면 비교가 성립하지 않는다.
  실제로 규칙 6 변경을 A/B 로 재서 **기각**했다(part 7/9 → 6/9).

> 리포트의 `이전 결과(...) 대비` 줄은 **직전 리포트와 무조건 비교**한다 — 문항 수·회차·
> 모델이 달라도 그냥 뺀다. 3문항 실행 뒤 20문항 실행을 하면 `+37.8pt` 같은 무의미한 값이
> 인쇄된다. **그 줄을 근거로 쓰지 말 것.**
