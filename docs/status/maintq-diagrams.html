행위자는 정비사와 팀장 둘뿐입니다. 이 그림의 요점은 기능 목록이 아니라 두 액터의 권한이 어디서 갈리는가 — 승인·반려로 가는 점선이 그것입니다.

② 시스템 구성 — 쓰기 경로가 둘로 갈린다

프로세스 2 · 도구 7

이 프로젝트에서 가장 중요한 그림입니다. MCP 도구는 DB에 INSERT만 할 수 있고 UPDATE 권한이 아예 없습니다. 상태를 바꾸는 경로는 사람 전용 API 한 곳뿐입니다.

이 그림이 지켜지는지는 회귀로 검증됩니다. spikes/write_tool_contract.py가 쓰기 도구의 계약을, spikes/api_contract.py가 상태 전이 권한을 확인합니다. 도구에 UPDATE를 추가하는 코드는 리뷰 이전에 회귀에서 먼저 잡힙니다.

③ 데이터 흐름 — S1 진단→발주 한 턴

시퀀스

"iG5A에 OHT 에러가 떴다"는 한 문장이 발주 초안 카드가 되기까지. tool_call이 도구 호출 직전에 발행되는 게 핵심입니다 — 그래야 trace 패널이 "실행 중" 상태를 보여줄 수 있습니다(A1).

④ 사용자 액션 — 진단 콘솔 /technician

화면 A

정비사가 마우스로 하는 일. 같은 자리에 오는 카드가 상황에 따라 달라집니다 — 발주 카드일 수도, 보류 카드일 수도, A/S 안내일 수도 있습니다. 화면 A는 진입 모드가 셋이라 그것부터 갈립니다.

발주 카드 자리에 보류 카드가 옵니다. 반복 고장일 때 PoDraftCard 대신 PoHoldCard(po_card variant hold)가 같은 위치에 렌더됩니다 — 발주 버튼이 없는 카드입니다. 원인이 확정되기 전에는 부품을 사지 않는다는 판단이 UI 형태로 나타난 것입니다(D35).
붉은 갈래가 이 프로젝트의 자부심입니다. error_codes가 아직 0행이면 lookup_error_code는 not_found가 아니라 catalog_not_loaded 에러를 돌려주고, 화면에 붉은 점으로 정직하게 실패합니다(D50). not_found를 줬다면 모든 코드가 S4로 흘러 환각률 지표가 가짜 100%가 되고 스모크도 위양성으로 통과했을 겁니다. 2026-07-28 실 Gemini 라이브 검증에서 이 동작이 확인됐습니다 — 에이전트가 공백을 지식으로 메우지 않고 그대로 안내했습니다.

⑤ 사용자 액션 — 승인 큐 /manager · 상태 전이
