② 시스템 구성 — 쓰기 경로가 갈린다

이 프로젝트에서 가장 중요한 그림입니다. MCP 도구는 DB에 draft INSERT만 할 수 있고 UPDATE 권한이 아예 없습니다. 상태를 바꾸는 경로는 사람 전용 API 셋뿐입니다. Sprint 7에서 쓰기 도구가 1 → 2종, Sprint 9에서 2 → 3종이 됐지만 이 원칙은 그대로이고, 오히려 커넥션까지 분리해(repair_writer() 신설) 강화됐습니다. Sprint 11은 읽기 도구만 7 → 9종으로 늘렸습니다(track_deadlines·assess_risk_grade) — 쓰기 도구는 손대지 않았습니다.

이 그림이 지켜지는지는 회귀로 검증됩니다. spikes/write_tool_contract.py가 쓰기 도구의 계약을, spikes/api_contract.py가 상태 전이 권한을 확인합니다. 도구에 UPDATE를 추가하는 코드는 리뷰 이전에 회귀에서 먼저 잡힙니다.

⑪ RAG dense(임베딩) 검색 흐름 — DB가 Postgres로 바뀐 뒤

신규 · Sprint 16 D116·D117, 2026-08-24
⚠ 위 ②의 "테이블 24"는 이제 낡았습니다. Sprint 16(D116)이 SQLite→Postgres 전환을 완료했고, D117이 manual_chunks 테이블(pgvector, 2,048차원)을 더해 테이블 25개가 됐습니다. DB 자체도 SQLite 파일이 아니라 DATABASE_URL이 가리키는 Postgres 인스턴스입니다 — 위 다이어그램의 "쓰기 경로가 갈린다" 구조(사람 API ↔ MCP 쓰기 도구 3종, D10)는 그대로지만 강제 메커니즘이 SQLite의 CREATE TEMP TRIGGER에서 Postgres 영구 트리거 + 세션 GUC로 바뀌었습니다.
매뉴얼 검색은 이제 키워드 + dense 하이브리드입니다. 정비사 질문 → rag_search_manual 도구 → mcp_server/rag.py::search()가 키워드(IDF) 점수를 계산하는 동시에 dense_scorer.score()를 호출 → data/external/nvidia_embed.py가 질의를 NVIDIA API(nvidia/nemotron-3-embed-1b)로 임베딩(캐시 우선, data/cache/embeddings/) → Postgres manual_chunks에서 같은 기종의 사전 계산된 코퍼스 임베딩을 읽어 코사인 유사도 계산 → 두 점수를 가중 융합(현재 1.0/1.0 임시값)해 순위 결정. NVIDIA_API_KEY가 없으면 예외 없이 키워드 전용으로 물러납니다(D47의 dense=None과 동일한 정상 상태 — 매뉴얼 검색 기능 자체가 dense 설정 하나 때문에 죽지 않습니다).
